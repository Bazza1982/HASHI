## 1. 产品目标和最小实现

HASHI Fingerprint 是一个可开关的、由程序执行的 Agent 变更标记系统。打开开关后，Agent 修改过的代码或文件，在允许的情况下自动留下可供其他人发现和检查的标记。现有日志是背后的证据，不是这个功能的全部。

开启后，每次纳入覆盖范围的修改，都应回答三个问题：

1. 这个文件是否经过 HASHI Agent 修改？
2. 哪个 Agent、在哪次任务中，造成了哪一次版本变化？
3. 接收文件的人，怎样检查这个标记与当前文件是否匹配？

最小可用版本由三部分组成：

| 部分 | 做什么 | 放在哪里 |
|---|---|---|
| Fingerprint Marker | 让别人发现这里有 HASHI Agent 的修改记录 | 安全的源码注释，或随文件交付的伴随文件 |
| Fingerprint Receipt | 记录身份、操作、修改前后哈希、结果和证据等级 | 复用现有 Canonical Audit |
| Fingerprint Manifest | 将文件、版本和回执关联起来，供第三方查看、验证 | 项目或交付包中的 `.hashi-fingerprint/manifest.json` |

关键原则：标记跟着产物走，详细证据保留在现有审计系统里。不能只在 HASHI 自己的日志里多写一条记录，就称为完成 Fingerprint。

产品功能名称为 `HASHI Fingerprint`，实现组件可称为 `Fingerprinter`，每次产生的证据称为 `Fingerprint Receipt`。文件哈希仅标识文件版本，不能单独证明是谁修改了文件；身份、操作和版本之间的关联才是需要补齐的审计能力。

## 2. 在当前 HASHI 中的架构位置

功能归 PAO，实现在 Functions 层。第一版不改受保护的 Core，不依赖改造外部前端，也不引入新的常驻服务。

当前源码已有合适的接入位置：

| 现有位置 | 已有能力 | Fingerprint 增量 |
|---|---|---|
| `tools/registry.py` 的 `execute()` | 集中执行 HASHI 工具，处理准入、执行及结果 | 在修改前建立操作身份、捕获前状态，在修改后完成回执 |
| `orchestrator/execution_resources.py` 的 `tool_resource()` | 对已接入的文件修改、Patch、Shell 提供资源租约和串行控制 | 将前后状态捕获放在同一个受控执行区间内 |
| `tools/effect_receipts.py` | 对部分 `file_write`、`apply_patch` 读回文件并计算哈希 | 复用观测结果，补齐前状态和 Fingerprint 关联，避免重复读文件 |
| `orchestrator/canonical_audit.py` | 持久化审计链、事件身份、内容寻址证据 | 增加 Fingerprint 事件类型，保持它作为权威证据来源 |
| `orchestrator/permissions/` | 受监督执行、文件操作和回执相关实现 | 对接同一套 Fingerprint 数据契约，不另造一套权限逻辑 |
| `adapters/` | 不同 Engine 的执行与事件转换 | 标明原生工具修改的实际覆盖情况，提供可用的变更线索 |

目前 `ToolRegistry` 的效果回执生成在执行租约释放之后。Fingerprint 的修改前后取证应放到租约内部，否则其他受控操作可能在两次观察之间改变文件。

基线源码依据：[工具执行位置](https://github.com/Bazza1982/HASHI/blob/2c38f313ac9ec64b8e1593d330b1fb65732bcc3b/tools/registry.py#L1002-L1019)、[现有效果回执位置](https://github.com/Bazza1982/HASHI/blob/2c38f313ac9ec64b8e1593d330b1fb65732bcc3b/tools/registry.py#L1193-L1212)、[资源租约实现](https://github.com/Bazza1982/HASHI/blob/2c38f313ac9ec64b8e1593d330b1fb65732bcc3b/orchestrator/execution_resources.py#L178-L210)。

这些租约只能协调参与同一机制的执行路径，不能据此声称已经锁住人工编辑器或所有外部程序。

已有基础还包括 [Canonical Audit 的持久化和链校验](https://github.com/Bazza1982/HASHI/blob/2c38f313ac9ec64b8e1593d330b1fb65732bcc3b/orchestrator/canonical_audit.py#L426-L535) 及 [现有效果回执](https://github.com/Bazza1982/HASHI/blob/2c38f313ac9ec64b8e1593d330b1fb65732bcc3b/tools/effect_receipts.py#L88-L123)。复用这些能力，不建立第二份竞争性的权威审计历史。

## 3. 开关和用户体验

第一版只提供一个清楚的主开关：`Fingerprint OFF / ON`。先不要增加 OBSERVE、ENFORCE、STRICT 等额外运行模式。

拟新增的启用配置示例：

```json
{
  "fingerprint": {
    "enabled": true,
    "marking": "auto",
    "export_content": false
  }
}
```

具体规则：

- OFF：不新增 Fingerprint 标记和回执；现有日志继续工作。
- ON：对支持的修改自动取证、生成回执，并按文件类型选择标记方式。
- 安装和升级不擅自开启该功能；用户选择开启后才执行新增标记行为。
- 开关由用户或获授权的管理入口控制，不作为模型可以自行设置的工具参数。
- 每次 Run 固定其启动时的 Fingerprint 策略版本，避免运行中切换造成解释不清。
- 开启、关闭、范围变化本身留下管理审计事件。
- 关闭不删除以前的标记和证据，也不追溯性地取消已有记录。
- 配置持久化复用现有配置所有者和修订冲突处理，不新增绕过 `orchestrator.config_json` 的直接写入路径。

正常使用不应多出审批弹窗。Agent 不需要依靠“记得签名”的提示词。

在拥有不受限制 Shell、与 HASHI 同等系统权限的执行环境中，仅靠配置管理无法保证 Agent 绝对不能修改配置或证据。第一版明确这个边界，不因此强制用户升级全部权限等级。

## 4. 标记怎样留在代码和文件上

### 4.1 源码使用短标记，不堆砌历史

对于已经实现并验证过安全插入规则的源码类型，可以加入一个短注释：

```python
# HASHI-Fingerprint: hfp_7c92d4...
```

这个 ID 标识文件的来源记录入口，不直接放完整历史。

同一文件以后再被修改，不不断追加名字和时间戳。详细版本历史进入回执；Manifest 指向相关版本。

插入规则必须考虑：

- Shebang、编码声明、许可证头。
- 文件编码和换行符。
- 语言或工具要求的特殊首行。
- 生成文件、快照测试、字节精确比较及签名文件。
- 已存在的 HASHI 标记和其他人的注释。

不能仅凭扩展名判断“加注释肯定安全”。格式适配器未经验证，就使用伴随标记，不试探性修改源码。

### 4.2 不适合内嵌标记的文件使用伴随证据

JSON、二进制、图片、模型、签名文件等，默认不向内容中硬塞文本。

项目采用：

```text
.hashi-fingerprint/manifest.json
```

单独交付一个文件时，可以生成：

```text
report.xlsx
report.xlsx.hashi.json
```

伴随文件记录目标文件的精确哈希和回执关联。

已有文件或同名目录不能直接覆盖；必须确认它属于本功能管理的命名空间。Fingerprint 也不能借“留下标记”扩大写入权限。

### 4.3 明确随产物携带的实际边界

项目复制或打包时，应把 Manifest 一起带走；单文件导出应附带伴随证据。

如果接收者只复制了一段代码、去掉了注释，或者只拿走原文件而不拿伴随文件，第一版不能保证标记仍然存在。这不是不可移除的隐形水印。

第一版的目标是自动、可发现、可验证的来源标记，不是抗一切删除和变换的水印。

## 5. 每次修改的执行流程

受控文件写入按以下顺序完成：

1. 从可信运行上下文取得 Instance、Agent、Conversation Session、Run 和 Tool Call 身份，生成独立 `operation_id`。
2. 完成原有权限检查，取得原有文件执行租约。
3. 读取目标的实际前状态，记录是否存在、精确字节哈希及必要的文件身份信息。
4. 持久化“准备执行”的记录。
5. 执行用户原本要求的修改，并应用允许的标记策略。
6. 读回最终状态，计算实际落盘字节的哈希。
7. 持久化结果回执，再生成或更新 Manifest 投影。
8. 返回业务结果，并附上独立的 Fingerprint 状态。

如果插入了源码标记，最终文件哈希必须包含标记本身。标记里只放 ID，不放自身文件哈希，避免循环依赖。

“持久化”必须表示已经完成相应的持久化确认，不能把仅进入内存队列视为落盘。接入现有缓冲写入器时，必须验证其 flush/barrier 语义；文件修改与审计写入不是天然的同一个原子事务。

回执至少包含以下字段：

| 字段组 | 内容 |
|---|---|
| 身份 | Instance、Agent、Conversation Session、Run、Tool Call |
| 操作 | Operation ID、创建／修改／删除等动作、执行入口 |
| 目标 | Artifact ID、受控根标识、相对路径 |
| 版本 | 修改前哈希、修改后哈希；不存在使用明确状态 |
| 时间 | 执行开始、实际观察、证据记录时间 |
| 结果 | 业务执行状态、取证状态、标记状态 |
| 可信程度 | 受控执行证据、Engine 报告、区间观察或归属不明 |
| 关联 | Canonical Audit 事件 ID、策略版本、已有权限回执引用 |

不能把三个结果合并成一个简单的“成功／失败”：

```text
业务修改：已完成
取证回执：已持久化
产物标记：待补写
```

这是合法且重要的中间状态。

文件已经写成功，但 Manifest 写失败时，不能把整个工具操作报成普通失败，让 Agent 重复执行。应只重试证据投影或标记补写。当前源码已经明确提醒：观测失败不能把已经产生的副作用变成可重试失败。[现有处理原则](https://github.com/Bazza1982/HASHI/blob/2c38f313ac9ec64b8e1593d330b1fb65732bcc3b/tools/registry.py#L1203-L1210)

## 6. 覆盖范围和证据等级

不能假定所有 HASHI Agent 的修改都经过 `ToolRegistry`。例如当前 Codex 适配器明确保留普通本地编程工具，并把部分文件变化转换为 Engine 返回的事件。接入 HASHI 工具网关不等于接管其所有原生文件写入。[Codex 原生编程路径](https://github.com/Bazza1982/HASHI/blob/2c38f313ac9ec64b8e1593d330b1fb65732bcc3b/adapters/codex_cli.py#L741-L798)

第一版采用以下覆盖表：

| 修改路径 | 第一版处理 | 可以声称什么 |
|---|---|---|
| HASHI `file_write`、`apply_patch` | 在受控执行边界捕获前后状态，自动标记 | HASHI 观察到这次工具操作对应的版本变化 |
| 已验证接入的受监督文件执行路径 | 复用执行侧证据，转换为统一回执 | 保留原执行侧能够支持的证据强度 |
| HASHI Shell／Bash | 记录命令身份及可获得的变更观察；不能只解析命令文本 | 某些变化在该执行区间内被观察到 |
| Codex／Claude 等原生工具 | 接收 Engine 事件，结合限定范围的文件观察 | 标明 Engine 报告或区间观察，不冒充受控写入 |
| 人工与多个进程同时编辑 | 标为冲突或归属不明 | 不把所有变化强行归给 Agent |
| 外部 API、网页操作、数据库 | 第一版保留操作关联，另行增加资源适配器 | 不声称已具有文件级来源验证 |

特别禁止：

- 把 `git diff` 中所有变化都记到当前 Agent 名下。
- 把“没有记录到其他变化”解释成“没有发生其他变化”。

已有未提交修改必须保留。Fingerprint 以本次操作开始时的实际状态为前状态，不以 Git HEAD 代替。

对于 Shell 创建的子进程、后台任务，任务结束不一定意味着写入结束。回执必须保留“后台执行尚未结束／观察不完整”的状态，不能提前宣称覆盖完成。

对归属不明的观察，不得自动生成肯定式的 Agent 作者声明。即使保存了来源索引，也必须将其证据等级与不确定性一起展示。

## 7. 第三方检查和导出

第一版提供独立的检查和导出入口。以下是拟实现的命令接口，不是现有命令：

```bash
hashi fingerprint status
hashi fingerprint inspect path/to/file
hashi fingerprint verify path/to/project
hashi fingerprint export path/to/project --output evidence.zip
```

第三方不需要获得完整聊天记录、系统提示词或全部运行日志。

导出包只包含必要信息：

- 文件与 Artifact ID 的对应关系。
- 纳入导出范围的 Fingerprint 回执。
- 文件版本哈希。
- 覆盖范围、排除项、未完成事项。
- 验证说明及机器可读结果。
- 经明确选择才包含的 Diff 或文件内容。

默认不导出密钥、工具原始参数、绝对个人路径和完整对话。可携带的 Manifest／伴随文件也遵守同样的信息最小化规则，不能以“自动生成标记”为理由将完整内部审计记录发布到目标项目。

检查结果应分开显示：

| 检查项 | 示例结果 |
|---|---|
| 当前文件与记录版本是否一致 | 匹配／不匹配 |
| 导出的回执结构及关联是否一致 | 完整／缺失／损坏 |
| 修改归属的证据类型 | 受控执行／Engine 报告／区间观察／不明 |
| 覆盖是否完整 | 在声明范围内完整／存在缺口 |
| 来源是否经过可信签名认证 | 已验证签名／未签名／信任来源未知 |

第一版可以先提供哈希与关联校验，但不能将其宣传为密码学意义上的作者认证。攻击者如果能够一起改文件和未签名 Manifest，就能伪造一套自洽数据。

独立签名、可信公钥分发和外部证据保管作为后续增强，不作为第一版上线的前置条件。现有审计链也不能单独证明拥有同等系统权限的人没有重写全部历史。

选择性导出不等于整个审计链的完整性证明。验证结果必须限定为导出包声明的范围，不把省略的内部事件伪装成一条完整原始链。

## 8. 故障、性能和保密要求

### 8.1 故障处理

- 写入前无法建立必要的持久化操作记录：只暂停这次需要保证取证的受控修改，给出具体原因；聊天、读取和其他无关功能继续。
- 修改后记录失败：保留准备记录，将结果标为待核对或未知，不自动重放业务修改。
- 源码不适合加注释：自动采用伴随证据，不阻塞正常工作。
- Manifest 暂时不能写：保留权威回执，显示“标记待补写”，不能显示已完整标记。
- 文件在补写前又被修改：重新核对版本，不把旧回执贴到新内容上。
- 重启恢复：只核对和补齐证据，不自动重新执行原工具。
- 删除文件：保留删除回执和 Manifest 中的删除记录，不试图给不存在的文件加注释。

### 8.2 性能要求

- OFF 时没有额外文件扫描、内容哈希或后台监听。
- ON 时优先复用工具已经读取的字节和现有效果回执。
- 不在每次工具调用后扫描整个仓库。
- 不增加一个持续轮询磁盘的常驻进程。
- 大文件采用流式处理；暂未完成哈希时明确标为待完成，不能假装验证成功。
- Manifest 是可重建投影，不建立第二份与 Canonical Audit 竞争的权威历史。
- 性能验收记录实际额外延迟、读写量和空闲 CPU，不在未测试前承诺毫秒数字。

### 8.3 信息保护和生命周期

内部回执和对外交付的来源数据分开投影，敏感身份信息与内容按照现有授权规则处理。证据导出不得改变受监督执行的权限含义，也不得为了生成哈希重新绕过受控文件句柄读取受保护目标。

Fingerprint 内部的 Manifest／伴随文件写入应有明确的系统派生来源，不形成递归“给标记再加标记”的循环。

历史标记只证明所引用版本的记录。后续文件内容不匹配时，显示不匹配或未知，不能因为仍留有一条注释就声称当前整个文件由 Agent 产生。

## 9. 代码组织和开发顺序

建议新增一个小的 `orchestrator/fingerprint/` 包，保持单一功能归属。具体文件拆分以实际代码规模为准，不为每个概念单独建一层框架。

| 拟新增模块 | 职责 |
|---|---|
| `models.py` | 回执、覆盖状态、策略版本的数据契约 |
| `service.py` | 修改前准备、修改后完成、失败恢复的协调 |
| `markers.py` | 安全源码标记和伴随标记 |
| `manifest.py` | 生成、合并和重建产物索引 |
| `verify.py` | 文件版本、证据关联及覆盖检查 |
| `export.py` | 最小化、脱敏的证据包导出 |

现有调用方只增加窄接口。不要把新逻辑继续堆进已经很大的 `ToolRegistry`。本功能的 Artifact Fingerprint 与现有 Runtime／Core fingerprint 不是同一种身份，不混用命名、状态或验证结果。

按以下顺序串行开发，每一步验收后再进入下一步：

| 阶段 | 开发内容 | 验收出口 |
|---|---|---|
| 1 | 数据契约、开关、可信身份上下文、Canonical Audit 接入 | OFF 无行为变化；ON 可生成可追溯回执 |
| 2 | `file_write`、`apply_patch` 的修改前后取证及恢复 | 创建、修改、无变化、失败、取消均有正确结果 |
| 3 | 源码短标记、Manifest、单文件伴随证据 | 别人拿到项目或交付包能够发现并检查标记 |
| 4 | Shell、原生 Engine 事件和受监督路径的适配 | 覆盖矩阵准确，不错误归属、不声称全覆盖 |
| 5 | Inspect、Verify、Export、文档和本机验收 | 可独立检查，且不依赖导出完整私有日志 |

阶段 1、2 是底座；阶段 3 完成后才算交付“留下指纹”。只有后台回执、没有产物标记，不算这个功能完成。

开发前重新核对当前分支及 main 的变化，保留其他人的工作；不得因为这份计划而回退后续已合并修改。实现期间遵守仓库 AGENTS.md，更新拥有该行为的文档和 FYI，并分别记录源代码实现、离线测试和实际采用状态。

## 10. 必须通过的验收用例

本地 Agent 至少完成以下测试：

1. OFF 时，生成文件内容、工具行为和既有日志行为不变。
2. ON 时，新建和修改支持的源码，自动产生标记与回执。
3. JSON、二进制和签名文件不被强行注入文本。
4. 同一文件反复修改不会不断堆叠注释。
5. 相同内容写回记录为无版本变化，不夸大成新修改；如首次加入标记改变了字节，单独反映标记造成的变化。
6. 已存在的人工未提交修改被保留，不被错误归属。
7. 两个 Agent 修改同一文件时，版本关联不串线。
8. 人工或外部进程并发修改时，冲突和证据不确定性可见。
9. Shell 部分执行后失败，仍检查已产生的变化。
10. 写入后审计或标记失败，不导致业务操作自动重复。
11. 进程在准备、写入、回执、Manifest 各阶段崩溃，恢复状态正确。
12. 文件删除、移动及复制能够正确处理，不能仅凭哈希相同就视为同一个文件。
13. 第三方修改文件后，验证结果显示版本不匹配。
14. 导出包不包含未获允许的密钥、聊天内容和个人路径。
15. 原生 Engine 未覆盖的路径明确显示缺口。
16. Windows 实机验证换行、路径大小写、长路径、文件占用及权限失败。
17. Core 保护检查通过；没有为本功能改动受保护 Core。
18. 开关关闭、开启及功能采用后，普通开发流程和空闲资源占用没有明显退化。

新建或实质重写的行为测试应提供可信的 red／green 依据，验证可观察行为与持久化失败边界，不用源码子串或“文档写了某功能”作为功能完成证据。

文档阶段按 Testing Policy 进行链接、结构、差异和 Core 边界检查，不以无关的全量测试代替适当检查。实现阶段按改动所属模块选取 focused／component 测试；涉及共享注册表、配置或执行边界时，运行相应 core gate。Windows／平台和实际采用测试单独报告，不把跳过当作通过。

实际部署、热采用和重启仅在明确授权的实例和范围内进行。Agent-local 与 shared Functions 采用分别遵守现有 `/reboot` 作用域，不采用冷重启作为本功能的默认交付路径。

## 第一版完成定义

复用 Canonical Audit，在受控修改边界生成 Fingerprint Receipt，自动给安全的源码加短标记，其他产物使用 Manifest 或伴随文件，并提供独立验证工具。

最终交付必须能把 HASHI 从“自己保存了详细日志”，推进到“交给别人一个产物时，也能交代它的 Agent 来源与版本证据”，同时保持覆盖声明诚实、正常工作可用、运行开销可控，不把第一版变成全面重建权限和安全系统的工程。
