# FC 标准接口补齐与接入收敛：具体执行计划

日期：2026-09-25；2026-09-26 更新。版本：3。状态：M1/M2 源码已收敛，等待干净提交后的最终资格门禁；M3 运行采用与现场交付尚未执行。

执行目标：完成一套可独立验证的标准 FC 公共接口，让命令、消息、显示、媒体和投递共用同一套语义与状态。现有 Connector 负责连接、格式转换、能力差异和回执；以后新增前端只需接入这套契约。

实施对象：HASHI1 候选分支 `feature/fc-unified-io-20260925`；外部 Workbench 的必要接入工作沿用 `agent/fc-unified-io-20260925`。本文已纳入 HASHI1 候选分支，作为该候选的权威执行与验收记录。

功能负责人：Frontend Connector。工程层：Functions；平台差异和实例配置仍使用各自现有配置边界。PAO 保留 Session、Message、Run、Event、权限、执行和路线冻结的唯一状态所有权。Protected Core 不在本次变更范围内。

## 1. 本计划如何接续已有工作

已有 `HASHI_FRONTEND_CONNECTOR_UNIFIED_IO_REPAIR_PLAN.md` 总方案和实施记录。本文件把剩余工作按用户最新确认的“标准 FC 优先，TUI 保持基本可用”重新排成执行清单。旧方案作为背景和历史证据保留；下一次开始施工时，将本清单纳入 HASHI1 候选分支并从原方案建立引用，后续只维护一份剩余任务状态。

本计划遵循 [系统架构](../ARCHITECTURE.md)、[分层边界](HASHI_LAYERED_RUNTIME_BOUNDARIES.md)、[FC 架构](HASHI_FRONTEND_CONNECTOR_ARCHITECTURE.md)、[测试政策](TESTING_POLICY.md)、[命令 UI 规范](HASHI_COMMAND_UI_STYLE_GUIDE.md) 和 [配置持久化规范](HASHI_CONFIGURATION_PERSISTENCE.md)。实施时以目标候选分支中的对应规范为准。

### 已有基础和必须补齐的部分

| 已有内容，可复用 | 当前限制，本计划要解决 |
|---|---|
| FC 版本化契约、校验器、能力查询与静态 Connector 目录 | 尚不能完整描述运行中的 endpoint、可用能力及 generation；公布一种 schema 不等于所有路径已实现 |
| Session Runs、附件 stage/upload/commit、命令结果持久登记 | 尚未把所有入口收敛到同一个接纳服务，部分旧路径仍会直接执行或提交 |
| meter/HER 卡片先记 Session、部分后台投递队列 | 尚无覆盖所有输出的统一事件流和逐目的地投递器 |
| Workbench 文字、附件、Canvas、语音等接纳适配 | 输入已有较多迁移，展示还依赖多个来源合并；优先复用已做部分 |
| Telegram 原生命令/按钮与共享命令登记器 | 不等于整个 Telegram 输入、输出、offset 与回执已闭环 |
| 媒体路径权限检查、有序文件组、部分 typed relay 上下文 | 媒体全生命周期、所有工具出口、Remote/Exchange 回复关联和恢复仍需收敛 |
| TUI 现有修改和回归证据 | 保留当前功能；本次不要求全面改写 TUI 或把它迁到完整 v2 显示协议 |

已有测试报告属于各自源码切片，不相加成“总体完成率”，也不证明运行服务已采用。此前组合测试出现过跨 Session 历史顺序/完整性失败，单独与复跑通过但根因未确定；早期 generation 测试也曾因未提交的工作树失败。这两项要在候选交付前完成核实，不能靠反复重跑取得一次绿色后销项。

## 2. 范围、完成层级与接口边界

### 本次范围

- 统一 FC 接纳、命令/控制、事件与显示模型、媒体服务、投递与回执。
- 把前台答复、错误、后台通知、调度输出、meter、HER 卡片、命令卡、审批和工具产物接到公共接口。
- Telegram、Backend/Session API 和外部 Workbench 做必要接入；HChat、Remote、Exchange 保留其传输责任并使用同一套本地接口。
- 清点当前已启用的其他 Connector；已启用者执行相同接入要求，未启用者只声明真实支持范围，不为验证扩建前端。
- TUI 只做已有核心功能回归；共用接口导致的实际回归允许最小修正。外观、主题、新交互、完整多 Session UI 不列入本次施工。

### 三个可分别验收的结果

| 里程碑 | 必须满足的条件 |
|---|---|
| M1：标准 FC 公共闭环完成 | 步骤 00—06 通过；参考 Connector 可独立完成接纳、事件、媒体和投递恢复，不依赖 Telegram/Workbench 运行 |
| M2：现有接口迁移完成 | 步骤 07 通过；所有本次范围内的入口和出口接到 M1，兼容入口有明确单一路径，TUI 基本功能通过 |
| M3：实际交付完成 | 步骤 08 通过；合格候选已被正确运行组件采用，指定真实前端验收、恢复与回滚演练完成 |

只能在 M3 通过后报告“本次 FC 修正和接口迁移交付完成”。M1、M2 可记录完成，但不能代替线上采用和真实收发证明。

### 标准化到哪里

公共接口规定命令含义、身份与权限、作用范围、防重复、事件顺序、内容组件、文件身份和回执语义。前端继续决定布局、字体和本地交互；Connector 根据能力渲染同一份结构化内容，能力不足时使用规定的安全降级。

“统一接口”是一组共用操作，不要求把所有行为挤进同一个 HTTP 地址。保留合格的 Persistent Session API，补足缺失契约；现有路由直接调用同一服务，不互相绕一圈 HTTP，也不再生成另一套 Session 数据。

| 公共操作 | 复用基础及明确补齐项 |
|---|---|
| 查询能力 | 复用 `/api/v2/frontend/capabilities`；区分协议支持、endpoint 注册、当前可用状态与运行 generation |
| 提交文字/媒体 | 复用 Session Runs API；各入口规范化为同一种 Ingress，再由同一个接纳服务调用 PAO |
| 命令、按钮、取消和确认 | 复用 Session commands、Run cancel、approval、voice-transcript decision 和共享命令登记器；统一身份、重复请求与结果查询规则 |
| 读取快照和增量 | 复用 Session snapshot/events/consumer ACK 的状态所有者；补标准 FC feed 的版本化投影，保留旧 v1 响应兼容 |
| 发布输出 | 新的公共发布操作调用 PAO 持久化边界；结果事件和投递任务原子关联，再交给 FC 分发 |
| 登记和获取媒体 | 复用附件 stage/upload/commit/bind 和现有授权；统一 MediaAsset/MediaGroup、保留规则和工具发布 |
| Connector 发送和回执 | 共用 dispatcher 调用 adapter 的渲染/发送能力；逐 event、逐 endpoint、必要时逐分片保存回执 |

业务命令目录继续来自 `command_specs.py` 及有效的运行注册；模型、语言和配置也从各自现有负责人派生。操作标识不从按钮文字反解析。

## 3. 执行顺序与推进规则

执行顺序为：00 基线清点 → 01 公共契约 → 02 统一入口 → 03 事件与显示 → 04 媒体 → 05 投递器 → 06 输出生产者 → 07 Connector 接入 → 08 交付。

步骤 04 的独立媒体工作可在步骤 02 完成后与步骤 03 并行；其余按依赖推进。每一步的退出条件是自动自检点，不是逐步向用户索要继续许可。后续收到执行指令后，在已有授权范围内连续推进，修复本次引入的失败并完成检查，再进入下一步。

每步记录：已有基础、实际修改、必要测试结果、未完成事项、下一步。只有范围选择、权限、数据取舍或外部条件确实需要用户决定时才停；预计耗时、任务较大、一次测试失败均不自动成为阻塞。

### 步骤 00：建立唯一清单，保留既有成果

交付物：入口—公共服务—输出目的地覆盖矩阵、已有修改归属清单、基线问题清单、实际启用 Connector 清单。

具体步骤：

1. 记录两份候选分支、未提交修改和运行 generation；保留他人的改动，必要时用独立候选工作树整合本任务文件。
2. 对每个入口和出口填写：当前调用方、权威状态负责人、标准接口目标、是否迁移、兼容路径、验证用例。
3. 入口至少覆盖 Telegram update/slash/callback、Session API、兼容 chat/admin/command、外部文字/文件/语音/Canvas、HChat/Remote/Exchange，以及内部任务源。
4. 输出至少覆盖 final/error/cancel、background/scheduler/proactive、meter/HER、command/approval、progress、attachments/voice、显式通知和工具产物。
5. 将已完成的 Workbench 输入和 Telegram 命令登记列为复用项；把 TUI 限定为兼容与基本功能回归。
6. 对已知历史分页/排序波动建立可复现的受控时钟和并列时间场景；先确定是产品排序还是测试环境问题，再限定修复范围。
7. 确认保护检查和工程 hook；实际开发时按现有安装器保留自定义 hook。本轮计划编制不安装或改动 hook。

必要验证：核对每行真实调用关系；针对历史测试波动运行对应场景；选定改动文件前执行 Core 保护检查。

退出条件：所有当前已启用入口和本任务输出都有明确负责人及迁移落点；已做工作不再当作新工作重做；无未归类发送旁路。

### 步骤 01：冻结可执行的标准 FC 契约

交付物：契约操作表、版本/错误/回执语义、Connector 接入说明、参考 Connector 的共用验证入口。

具体步骤：

1. 在 `frontend_contracts.py` 等现有负责人上补足 Ingress、Event、Command/Control、DeliveryIntent/Receipt、MediaGroup 和 Relay 的必要字段及校验。
2. 为每个操作写清请求、接纳结果、终态查询、作用范围和幂等键；明确未知版本、过期、内容冲突、权限错误和结果未知的处理。
3. 把静态 Connector 目录补成从实际注册 adapter 派生的能力快照。endpoint 绑定经过验证的主体、实例和允许作用范围，附带当前可用状态与 generation；不用客户端自报授予权限。
4. 能力公布只描述已实现且已就绪的操作；未知或尚未实现的能力不以 schema 版本代替证明。旧 source/surface 名称仅在兼容 adapter 中归一化。
5. 定义参考 Connector：用新的已注册 ID 接入相同契约，具备普通文本、结构化卡片和媒体引用的最小收发能力；可模拟拒绝、超时、失联及能力不足。
6. 定义统一内容组件：文本、状态/键值、表格、动作、提示和媒体引用。语义字段由公共服务产生；locale、转义和能力降级由共享展示规范约束。

必要测试：T01、T12；扩展已有 `test_frontend_contracts.py` 和能力 API 场景，验证真实校验与注册结果，不用复制文档文本的断言。

退出条件：操作表中每个操作都有负责人、字段、错误和回放规则；参考 Connector 能完成能力协商；前端名称不决定命令业务或权限。

### 步骤 02：补齐统一入口、命令与控制服务

交付物：所有 adapter 可调用的共用接纳服务，以及持久接纳/拒绝/重复/冲突/未知结果。

具体步骤：

1. 在 Functions 建立公共 ingress 服务，复用 SessionStore 和 PAO 接纳事务；候选模块名为 `frontend_ingress.py`，不建立第二套业务数据库。
2. 统一完成主体与目标验证、Session/context generation 核对、内容限制、已提交媒体绑定及路线冻结，然后分别调用已有的消息、命令、取消和确认执行者。
3. 复用 `frontend_command_admission.py` 的预留和完成登记。接纳身份必须能找回最初绑定的目标；`/new`、Session 切换或 context 改变后，相同 transport ID 不能在新 Session 再执行一次。
4. 并发相同键同内容只能接纳一次；同键不同内容返回冲突。已完成请求返回原结果，pending/unknown 不自动重跑有副作用的操作；敏感参数按原规则脱敏。
5. 命令、按钮、审批和取消保持 typed 动作，沿用共享命令目录。过期或已失效动作明确要求刷新；不能把控制请求退化为普通模型输入。
6. 将“请求已持久接纳”“仍待用户确认”“任务开始执行”分开。Safe Voice 等确认流程保留现有语义，未获确认不得启动相应任务或工具。
7. Telegram offset、Remote/Exchange ACK、外部草稿清除只能建立在相应的持久接纳结果上；网络响应不明时可查询同一请求，不能另造身份改走旧接口。

必要测试：T02、T03、T08；复用 `test_session_api.py`、`test_session_store.py`、`test_slash_command_audit.py`、`test_command_interaction_transport.py`。重点检查持久化、并发和实际处理器执行次数。

退出条件：参考 Connector 的文字、命令、控制和确认均通过同一接纳边界；Session 更换、并发及重启恢复均不造成重复副作用；PAO 仍是执行负责人。

### 步骤 03：建立统一事件流和显示模型

交付物：可快照、补读和恢复的标准 FC feed，以及通用结构化展示结果。

具体步骤：

1. 基于 SessionStore 的 Message/Run/Event 构造版本化投影；候选模块名为 `frontend_projection.py`。复用 `request_activity.py` 已分类且已过滤的临时活动，不暴露内部 provider 内容。
2. 定义持久和临时两类事件。持久事件使用 Session sequence；临时事件使用独立 epoch/sequence 及有效窗口。一个订阅面返回两类游标，不能比较或混合不同来源的数字序号。
3. 快照返回一致的持久水位；快照之后再补读不得漏掉中间事件。分页、Run 过滤、ACK 和新事件并发时，已确认水位不能越过未读取的持久事件。
4. 统一 message/event ID、Run/request 关联、替换关系和终态。临时预览被正式结果替代；临时进度丢失需声明 gap，不能覆盖已落盘的最终结果。
5. 命令处理器和卡片生产者返回通用内容组件；公共命令目录、状态和值保持同源。Telegram HTML、终端文本、网页组件只做显示映射。
6. 兼容 transcript 从该权威源派生；历史 JSONL 只作为标识清楚的旧数据补读，不再争夺新消息的权威性。旧 v1 消费者保持既定格式；新投影通过显式能力协商选择。

必要测试：T04、T05；复用 `test_chat_connector_projection.py`、`test_session_store.py`、`test_session_api.py`，补实际消费者读取与重连场景。

退出条件：参考 Connector 能读到完整持久内容并恢复订阅；客户端无需猜测 transcript、即时返回与 activity 的优先级；两种 renderer 的命令含义和状态一致。

### 步骤 04：补齐公共媒体与工具发布

交付物：所有 adapter 和工具共用的媒体登记、原子绑定、获取、发布和保留服务。

具体步骤：

1. 复用 Session attachment 和 audio asset 的现有所有者，建立统一服务入口；MediaAsset 是受管字节引用，MediaGroup 是一个用户动作的有序集合。
2. 统一 stage/upload/commit/bind 的摘要、大小、类型、重放和所有权校验。中途失败可以留下受管 staging，但不能启动不完整的用户任务。
3. 让 `frontend_send_attachments` 按当前已冻结路线发布媒体引用；显式 `telegram_send_file` 等旧工具名作为指定目的地的兼容包装，走同一授权、发布和回执边界。
4. 浏览器下载、Computer 截图及其他工具产物使用同一登记/发布接口；实际浏览器或设备操作继续归原 Worker 和权限负责人。
5. 检查授权 Workzone、symlink/junction 逃逸和读取中内容变化；外部调用者只持有 opaque asset ID，不能提交本地绝对路径获取文件。
6. 区分 staging、已绑定资产、传输缓存和 spool 的保留周期。清理先检查引用和在途投递；过期资产返回 tombstone，缓存缺失可从仍有效资产重建。
7. 保留 Safe Voice 确认、多文件顺序、caption、音频时长和已有长期保留策略；对旧附件记录使用可兼容读取或明确迁移。

必要测试：T08、T09；复用 `test_frontend_attachment_tool.py`、Session API/store 和外部 Session/voice 的真实适配测试。Windows junction 与 WSL symlink 分别使用相应平台场景。

退出条件：同一有序文件组从输入、工具输出到多目标投递均使用相同资产身份；失败不产生半个任务、越权文件或提前删除；旧历史附件可读取。

### 步骤 05：完成逐目的地的持久投递器

交付物：共用 dispatcher、逐 endpoint 的投递状态、失败恢复和可查询回执。

具体步骤：

1. 扩展已有 delivery outbox/receipt 实现；由 PAO 的持久化事务提交事件与所需投递任务，FC 负责领取、渲染、发送并回报。候选协调模块名为 `frontend_dispatch.py`。
2. 以 event ID + endpoint ID 标识一个投递目的地，分片另带稳定 part ID；不能仅按 Telegram/Workbench 这种 surface 名记录成功。
3. 用持久 claim、lease、attempt 和 generation 约束发送者；同一目的地同时仅允许一个有效发送者，旧 lease 不能覆盖新回执。
4. 明确发送前、发送中和已取得回执三种恢复边界。旧发送者可能仍在调用外部服务时，lease 到期不能直接导致第二次发送；先根据证明归类为安全重试或 unknown。
5. 明确 accepted、delivered、rendered、read、failed、unknown 的证明强度。拉取型前端的消费 ACK 不自动变成用户已读，也不借 Telegram 成功证明其他目的地成功。
6. 已知未提交或明确可重试的拒绝按预算重试；可能已发送的超时进入 unknown，保留核对入口。目标提供幂等或查询能力时使用它；没有这种能力时不承诺跨网络的绝对 exactly-once。
7. 一个镜像失败独立记录，其他目的地继续；运行中更改偏好不改变已接纳事件的目的地。毒性任务、超限和到期进入明确终态，避免无限循环。
8. 新旧发送责任通过持久模式/generation 切换；先处理旧在途状态，再交接。历史事件补录只补历史，不自动生成外部补发任务。

必要测试：T06、T07、T10；用真实 SessionStore、两个竞争的 dispatcher 和可控制故障的 adapter 测试事务与外部边界，复用现有 runtime delivery 测试。

退出条件：提交后未发送的任务可恢复；已知成功的分片不重发；结果不明的任务不被盲目重发或误标失败/成功；各目的地状态相互独立。

### 步骤 06：把所有输出生产者接到公共发布接口

交付物：入口—出口矩阵中所有本任务输出的标准发布路径；M1 验收结果。

具体步骤：

1. 按顺序接入 meter/HER/command/approval 卡片、前台 final/error/cancel、后台及 scheduler/proactive 通知、语音与工具产物。
2. 复用已有 canonical-event 和后台 outbox 代码，将尚存的直接发送调用收拢到 adapter。Engine/HER 返回语义结果；PAO 提交结果；FC 决定如何按冻结路线投递。
3. 一个助手答复的文字与可选语音 rendition 关联同一语义消息；一次命令也只产生一份持久结果，避免同步返回和事件回放各增加一条历史。
4. 显式通知保留用户指定目的地语义；没有当前聊天 Run 的内部通知使用明确的 PAO 事件来源和目标，不伪造用户输入或依赖 Telegram chat ID 推断身份。
5. 将 think/commentary/verbose、meter/HER 开关、locale 和内容隐私过滤保留在各自负责人，生成各 adapter 共用的可显示结果。
6. 用两个参考 endpoint 完成一次全闭环；再注册新的参考 Connector ID，运行同一公共契约测试，确认不需要修改命令、Session、权限和业务发布逻辑。

必要测试：T02—T12 中与本阶段连接点相关的场景；包含 `test_runtime_delivery.py`、`test_runtime_delivery_order.py`、`test_meter_cost_runtime.py`、`test_herv2_card.py` 和命令消费者。

退出条件：M1 达成；公共标准已能独立收发和恢复所有要求的语义类型。覆盖矩阵不再存在未解释的业务直发出口，第三个参考 Connector 只需注册和 adapter。

### 步骤 07：接入现有 Connector 和标准中继

交付物：逐 Connector 的薄适配及合格记录；M2 验收结果。

具体步骤：

1. Telegram：复用现有认证、polling、HTML/长消息、文件传输和 rate-limit 处理；将 update/slash/callback 送公共入口，把标准事件交现有传输 renderer，回执返回 dispatcher。补齐 offset 与持久接纳的边界。
2. Backend/Session API：现有合格路由调用公共服务，保留其公开版本语义。兼容 `/api/chat`、admin 和旧命令 transport 只做范围受限的转换；调用 admin 兼容路由不能给普通客户端附加权限。
3. 外部 Workbench：复用现有 Session 输入适配；将显示订阅切到标准快照/feed，并保持 connection、instance、Agent、Session、generation 的隔离。草稿、未读、置顶和布局仍由客户端负责，凭据保留在服务端。
4. HChat/Remote/Exchange：复用已有认证、信任、持久网络队列和 peer 路由；验证后的 RelayEnvelope 直接进入同一个本地 ingress，reply/error/media 通过 correlation/event 返回。展示文本不再承担身份或回复关联权威。
5. 旧 peer 只在声明的兼容能力范围内使用 adapter；带私有证明或已产生副作用的请求不能降级到会丢失授权语义的旧协议。未启用的 peer/Connector 保留未验收状态，不临时扩建部署。
6. TUI：保持其现有本地界面、命令和兼容读写路径；确认共用服务变化没有破坏基本行为。只修已复现的接口回归，不把完整 feed UI 迁移变成交付前提。
7. 每个实际 adapter 跑同一套公共符合性测试，加本传输独有的边界测试；不为每个前端复制一套命令业务、权限判断和整套业务测试。

必要测试：T10—T13；沿用已有 Telegram、command transport、HChat、Exchange、Remote 及外部代理测试。外部客户端先跑改动的 Session/voice/command/feed 消费者，候选发布时再跑既定 server、UI-policy 和 build。

退出条件：M2 达成；各实际 adapter 的接纳和结果语义一致，私有传输细节限定在 adapter；现有 TUI 基本流程可用，未迁移的兼容路径有准确清单及负责人。

### 步骤 08：资格检查、运行采用、现场验收和退役收口

交付物：可审阅的候选变更、离线资格结果、运行采用回执、现场验收记录、回滚验证与最终状态。

具体步骤：

1. 完成本任务文件的审阅、必要静态/组件检查及中央边界的 Core gate。仅将归属明确的本任务修改整理为干净候选，保留他人的未提交工作；依现有发布政策完成不可变 Function generation 资格检查。
2. 解决影响候选的已知测试波动和 generation 失败。旧数据库升级、旧 generation 兼容读、回滚后持久去重与未知投递保留均需有证据。
3. 冻结候选源代码和外部客户端版本；记录目标实例、Agent、启用 Connector 和测试目的地。先完成离线候选及具体采用方案，再核对现有授权是否覆盖所需运行操作。
4. FC 公共 API/dispatcher 属共享 Functions 时，采用需要覆盖共享 Functions 的热切换；单 Agent `/reboot min` 不能冒充共享采用。建议按现有运行集合选择受管 `/reboot same`，并核对共享进程、相关 Worker 与 Remote 的实际 generation。
5. 本计划不新增生命周期授权。此前一次 WSL 重启许可已使用；HASHI2 保持在线，其他实例不因本计划被改动或重启。若 HASHI1 共享热切换或真实跨实例测试缺少明确授权，在候选就绪后一次性列出具体目标与影响。
6. 按第 5 节 FC 现场清单执行真实前端验收、恢复与受管回滚。验收期间源代码冻结；发现需修复问题则结束该轮、修复并生成新的候选和验收基线。
7. 通过后进行至少 30 分钟受管观察，覆盖一次授权的断线恢复和所有实际启用目的地；没有自然故障不能替代故障恢复测试。真实业务中未解释的丢失、重复和 unknown 必须处理完；故障注入形成的 unknown 要有保留和处置记录。
8. 仅在对应目的地采用、验收和回滚通过后关闭旧发送旁路。TUI/旧客户端必要的兼容入口保留为已登记的薄转换；记录旧 peer 的兼容清单，不把兼容读接口存在本身判为失败。
9. 更新拥有行为的 FC 决策、接口文档、接入说明与 Agent FYI；汇总 M1/M2/M3，明确代码、运行采用、用户可见结果各自证据。

必要测试：T14、第 5 节现场清单；最终再次进行 Core 保护检查与源代码/运行 generation 核对。

退出条件：M3 达成；所有必需项通过，无未解释的失败或实际交付未知；回滚保存历史、去重和投递状态，Core 与非目标实例边界符合要求。

## 6. 回滚与真实阻塞

回滚按目的地和受管 Function generation 执行；恢复已验证代码和发送责任，不删除新产生的业务数据，也不使用工作树硬重置。代码回滚前必须确认旧候选能读取新增的持久格式；如不能安全回退则拒绝切换，保持当前受管状态并提交具体处置方案。

切换发送责任时停止该目的地的新领取，等待或识别在途请求；已成功的 event/endpoint/part 保持成功，unknown 继续隔离。不得清空队列、幂等记录或 lease 来强行制造“可以重试”。配置回滚沿用读取 revision；冲突或已提交但持久性不明时不能盲目再写。

确实需要用户介入的情形限于：

- 功能必须改变受保护 Core 或扩大既定产品范围，现有 Functions 边界无法实现且已有具体证据。
- 已完成可审阅的候选，但所需 HASHI1 共享热切换、外部客户端采用或指定 peer 的真实写入超出现有授权。
- 有数据损失风险或无法兼容的持久格式，需要用户在保留/迁移方案之间做取舍。
- 其他人的重叠修改经隔离候选仍无法安全整合，或缺少真实前端/认证条件且安全替代只能完成离线证据。

提出阻塞时一次说明已完成的结果、精确受阻动作、具体证据、推荐方案和替代方案。标准契约、公共实现和离线验证等独立工作应先完成；不在每个步骤结束时重复请求继续许可。

### 2026-09-26 标准接口收敛复核（提交前）

用户确认的设计已作为当前判据：FC 统一 message、command、display/card、
button/action、media 和 receipt 的语义；Connector 只负责身份/连接、传输、
本地样式与真实回执。TUI 等局部差异必须在 FC Registry 登记，不能靠未登记
旁路。外部前端和 Telegram 平台本身不在本次修改范围。

本轮完成了此前 6/10 复核留下的生产缺口：普通回复、命令卡和按钮、最终

endpoint outbox 为权威路径。Telegram HTML、inline keyboard、媒体发送方式、
