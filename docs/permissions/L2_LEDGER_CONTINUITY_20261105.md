# 权限账本备份连续性补验与修复（2026-11-05）

功能主责 PAO；工程层 Functions。直接消费者为 L1/L2 Safety 权限服务及其
HERV3 执行门。不改 Protected Core，不扩展批准来源、Workzone 或租约寿命。

## 实际发现

对 PR #133 集成版本使用真实 SQLite backup：先批准、备份，再撤销，随后只恢复
旧账本。旧实现既允许仍存活的 authority 使用恢复出的 grant，也允许重新启动
authority、绑定新 epoch 后使用该 grant。两项行为回归均实际失败。
单纯轮换 service generation 不能证明撤销记录没有被备份覆盖。

## 修复合同

账本升级到 schema 9，在现有受保护 Safety 私有目录内另存一个连续性见证文件。
它只保存最后一次事务的随机标记，不保存或授予权限；权限事实仍只有原账本一个 owner。
每个 authority 事务先核对两份标记，再在同一个 SQLite ATTACH 事务内原子更新。
包括被拒绝事务另外保存的可信时间下限，也遵循相同核对和提交边界。

两份数据库必须使用持久 rollback journal 和 FULL 同步，依赖 SQLite super-journal
共同提交；WAL、MEMORY 和 OFF 均拒绝，不静默改写原数据库模式。
见证写入失败时业务写入一起回滚。不存在“先提交授权、再补见证”的成功状态。

仅恢复旧账本、丢失见证或混入其它账本的见证时，正常调用与启动均拒绝。
不得通过删除见证、覆盖两份文件或重置数据库版本来恢复执行。
schema 9 还使旧 schema 8 程序拒绝该账本，避免回退程序写入不受见证保护的历史。

首次创建或首次从完整 legacy 安装升级时，在同一事务中建立初始标记，保留有效决定、
租约和任务。此初始绑定不能证明采用见证之前的备份历史；安装前必须核实真实来源。
已建立见证的安装不能把恢复出的 legacy 数据库当作首次初始化。

## 运维和发布边界

见证应与 Safety 账本采用同等私有目录保护，但必须排除在普通账本备份／恢复覆盖集合外。
安装及卸载清单需要明确登记它；不把它复制进 runner、模型上下文或普通任务文件。
普通 L0 路径不构造 authority，因此不创建、读取或依赖该文件。
正常 L1 决定、任务授权寿命及安全重启语义由原回归继续验证。

本修复选择无法证明连续性就拒绝执行。它**没有交付完整的显式恢复／升级／回退运维流程**：
恢复后任务进度和审计仍保留在原数据库中，但需要受信操作者对账，再重新确认缺失权限；
不得把启动拒绝当成已完成恢复。旧二进制不能直接读取 schema 9，也不能靠恢复旧授权备份
来回退。相关迁移、回退和故障恢复仍是 WAC30–32 的发布阻断项。

同机管理员或全机快照同时回滚账本和全部本地见证时，本机制不能识别；独立不可回滚锚点
不在首期保证内。保留 [Windows L2 第 6.4 节](L2_WINDOWS.md#64-回滚不能复活权限) 的范围。

## 验证与责任

负责人为 mimi，继续在 PR #133 原 feature-permission-sys 检出完成补验及修复；
用户不需要执行命令或改代码。原生安装、服务重启和最终前端窗口受本轮既有限制约束，
不能据离线结果关闭全部 WAC。

- 真实旧备份复现：旧实现两项失败，修复后两项通过。
- 缺失／空／不同账本见证均拒绝，原账本字节保留。
- 真实 SQLite trigger 制造见证写入失败：请求未提交；进程内“提前提交”变异会使该断言失败。
- 原 authority 与恢复模块组合检查覆盖正常租约、时间下限、并发、迁移原子性和恢复幂等。
- 两个真实子进程分别在提交前／后退出，恢复后分别保留原有效 lease／已撤销状态，两份数据库没有分裂。
- 实际执行原集成提交的 schema 8 程序：拒绝 schema 9；当前 owner 仍可合法使用原授权，未被失败候选挤掉。
- 完整 113 模块首次结果为 1307 passed、4 failed、3 skipped；四处失败均是旧迁移版本断言，保全／冲突回滚断言保留，更新后六个相关模块 97 passed。三项 skip 为 WSL mount、POSIX mode 和 POSIX symlink，不计通过。
- 300 秒工具等待超时与随后完成的 JUnit 分开：完整进程实际运行约 439 秒，其原失败报告保留。
- 完整最终版本的检查及仍缺实机步骤记录在 [WAC 补验责任表](L2_WAC_CLOSEOUT_20261105.md)。

上面是实现及软件边界证据，不是新版本已安装、已部署或完整 L2 已通过。

## Windows CI 等待复核

首次推送有一项 Windows CI 在 prepared 事件的一秒等待上超时（910 passed、
1 failed、3 skipped）；原完整日志保留。该用例用真实 SQLite、实际 registry 和
authority，但 launcher 由可观测文件夹具替代，不是在测一秒的产品性能承诺。

在同一个原用例的异步入口注入 1.1 秒合法调度等待，实际复现相同 TimeoutError；
单纯阻塞 event loop 的 sleep 没有复现，记录不充当 RED。仅将该模块准备／收尾的
死锁 watchdog 设为 10 秒，仍等待原 queued/prepared 事件，保持政策变更顺序、
最终 start 复核、实际文件不存在和写入数断言。产品 TTL、heartbeat、清理期限、
用户批准与所有 Fingerprint watchdog 均不修改。

仍须独立通过，不能用本地通过覆盖原远端失败。
