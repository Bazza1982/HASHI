## 2. 已证实问题与证据边界

- 管理链 _select_runtime、onboarding、TUI 存在向封存解释器的子进程漏传禁缓存参数；带 -B 的外层进程不会自动约束后续子进程。
- 原安装运行身份对标准库仍继承写权限。实际受控重现中，诊断退出 0 却新增 98 个缓存，随后严格资格失败；禁止写缓存的对照保持封存不变。
- 当前原安装只读核验：Core 的 base 标准库出现未登记缓存；Functions 的 tzdata 包出现三份未登记缓存。校验在文件集合阶段退出，尚不能声称其余主体字节都正确。
- rika 与 lulu 的相关工作区已生效。直接调用在工作区检查、执行器和权限审批之前，被运行资格异常整体拒绝。
- MCP 上下文删除了不可序列化的 _runtime 对象，却未补回等价的可信角色保护事实；新进程也未绑定角色资格。离线上下文往返得到空的安装派生保护目标。
- 原始异常被压成“受控恢复”，随后被错误归入普通 permission_denied / command_error；在线、能回复和 Scheduler completed 又不能证明业务已执行。

## 4. 先建立正确行为契约

### 4.1 两个事实不能混成一个开关

PAO 分开持有：

1. **可信保护边界**：来自既有已准入私有运行事实的 Core/FR/base、清单、选择记录、Core PID、秘密路径、服务目标和工作区/Run 身份。是保护哪些对象的依据。
2. **当前安装资格**：对同一安装当前完整字节集合的核验结果，含具体角色、失败类别和有限的脱敏差异。是能否新启动、采用或运行该安装的依据。

Functions 启动/准备时建立不可由 Agent 修改的保护快照；选择新 FR 时原子合并已绑定旧 FR 与已验证新 FR 的目标。后续完整性失败不能抹掉已有保护，也不能被转化为整个工作区失效。

不允许用提示词、工具参数、Agent 可写配置、一个环境变量或空字段自选身份/保护根。文件名、schema 号和 owner-only JSON 本身都不是可信角色证明。

### 4.2 故障状态与动作矩阵

| 动作 | 安装有效、可信边界完整 | 安装失配，但已有可信边界 | 缺安装事实，但现有读范围/身份仍可信 | 身份或读范围本身无法验证 |
| --- | --- | --- | --- | --- |
| 已授权业务文件/目录的只读访问 | 按原工作区规则 | 按原规则，排除秘密；返回实际读取结果 | 只允许能证明范围与秘密排除的只读操作 | 不进行业务文件访问；系统诊断仍可达 |
| 已批准文档查询与脱敏故障说明 | 可用 | 可用 | 可用的可信只读来源继续可用 | 系统提供不含秘密的故障状态与恢复负责人 |
| 普通工作区写入、明确独立开发工具 | 按原 L0/L1/L2 规则 | 只有受保护目标排除仍可证明时按原规则 | 无法证明写/执行边界的具体操作拒绝；不把空目标当许可 | 拒绝 |
| 改 Core/CR/FR/base、清单、选择器；读秘密；杀 Core；原始当前服务控制 | 继续拒绝一般 Agent 操作 | 继续拒绝 | 不因缺上下文而放行 | 拒绝 |
| 创建新 Worker/MCP、运行封存解释器、热采用候选 | 严格资格与现有运行协议 | 拒绝失格安装；清楚说明原因 | 缺可信资格即拒绝 | 拒绝 |
| 现有普通权限申请和查看审批状态 | 走现有 PAO 流程 | 原本可申请的操作仍可进入；不绕过不可批准禁区 | 可信控制通道可返回明确状态；缺执行证据不能先执行 | 可信 owner 诊断入口；不伪造审批单 |

约束：

- 工作区外访问不因用户聊天同意或审批按钮而自动扩权；沿用现有管理工作区与权限边界。
- 不为硬性完整性/秘密/Core 禁区生成“批准即可绕过”的假审批单。应解释“环境需要维护”，给受控恢复入口。
- 不对任意 shell 一概放行；正常业务读取优先使用已有受管结构化工具。独立工具执行仍满足原权限、目标判断和平台保护。
- 安装失配后的可用性保证针对已有可信驻留 Functions 及现有可信控制通道，不允许借此在失格 FR 中新起工具进程或任意加载代码。MCP 子进程退出后，恢复状态由已有 PAO 通道解释，不能不经资格重启它。
- 如实施发现只靠现有 Functions 私有接口无法兑现某项保证，单独记录那个步骤的真实阻塞及可行窄方案；不擅改 Core 或把不可信数据当收据。

### 4.3 诊断与审批的输出契约

一次拒绝至少派生并保留：故障类别、角色、当前实例/Agent/Run 关联、动作是否执行、可重试性、影响范围、有限的脱敏原因、可用恢复入口/负责人。具体字段复用现有 ToolResult、Smart Tool、审计和权限模型，不引入第二份权限状态。

本计划固定两类运行错误：runtime_integrity_failed（安装完整性失配）与 runtime_protection_context_unavailable（可信保护事实不可用）。现有权限/工作区拒绝保留原类别；实现同步合约后，T09 按稳定结构字段验证，不使用通用 permission_denied 掩盖完整性故障。

- 模型和用户看到可理解的原因；私人路径、令牌、密钥、完整清单与邮件内容不进入公共健康接口或普通提示。
- 普通权限待批准必须有真实申请 ID、确切动作和原 Run 约束；批准一次只执行一次；过期、撤销、换 Agent/Run、重放不产生副作用。
- 系统只读故障状态不依赖先通过正在故障的业务工具准入，也不加载失格环境来诊断它。
- 不能给出“重启一定解决”；只有已有资格、采用范围和运行授权都满足时，才展示实际支持的恢复动作。

### 5.3 重现环境和防止假绿

- 使用真实 CPython 与可抛弃的已封存角色夹具；不用不会执行的假解释器证明不写缓存。
- 构建/封存前允许缓存；封存后清除 PYTHONDONTWRITEBYTECODE、PYTHONPYCACHEPREFIX 等可能掩盖漏参的外部条件，再通过受支持入口执行。
- T02 的终端驱动不连接用户桌面；生产界面/实体设备检查如会干扰用户操作，另循现有同范围授权。
- 不 mock 资格校验成功、工具成功、保护目标、ACL 拒绝或回滚成功；mock 只用于安排可控输入或观察调用。
- 真实 MCP/直接通道各执行正向读与反向拒绝，不能以“上下文 JSON 有字段”作为唯一证明。
- 一个 pytest 进程共享一个默认临时根；确需并行的独立进程必须有不同 --basetemp。测试不隐式递归跑其它 pytest、不调用真实 Provider 或邮箱。
- Windows 原生和 Linux/WSL 分开保存结果。WSL 兼容默认在既有 HASHI2 的可用窗口验证；不让 WSL 通过替代 Windows ACL 证据，也不因 Linux skip 宣称两平台均通过。
