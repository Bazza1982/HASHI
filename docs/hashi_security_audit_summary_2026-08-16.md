# HASHI 安全审计统一汇总（高自主执行修订版）

- **日期：** 2026-08-16
- **修订口径：** 2026-08-16，按 HASHI 高自主执行原则重新筛选
- **审计对象：** HASHI 运行时（`/home/lily/projects/hashi`）
- **产品立场：** 默认给予受信 agent 宽权限、高能力和低摩擦执行环境；修 bug、管理信任边界和失控风险，但不以增加审批、缩小工具能力或默认沙箱化作为修复目标
- **证据范围：** 54 条有详细证据的观察项；另有 17 条只有分类计数、没有 ID/位置/证据，暂不进入修复排期

---

## 一、结论先行

原报告把“agent 能做高风险操作”和“未受信主体也能调用这些能力”混在了一起。按 HASHI 的核心定位，这两件事必须分开：

1. **宽权限不是 bug。** 整盘文件访问、shell、浏览器脚本、文件上传、跨目录修改、长循环、选择 Telegram 收件人，以及 Codex 关闭审批/沙箱，均可作为受信 agent 的正常能力。
2. **错误的信任边界才是 bug。** 如果本应只供本机受信 agent 使用的控制面被其他本地用户、局域网或外部调用者直接访问，应修复入口身份和部署边界，而不是削弱入口后面的工具。
3. **显式受限模式必须可信。** 默认可以大胆，但用户一旦明确选择 `read_only`、设备 scope 或受限 profile，所有执行路径都必须遵守该选择。
4. **优先修复不阻断工作的缺陷。** 崩溃、日志泄密/膨胀、失控子进程、协议帧无界、错误分类、状态丢失、静默回退和恢复损坏，都应优先修。
5. **不引入新的默认审批门。** 修复不得把人类逐次批准、命令白名单、URL 白名单、短硬超时、强制 workspace-only 或默认拒绝策略放进正常 agent 热路径。

因此，原报告中的“71 项发现”只能理解为 **71 条原始观察**，不能理解为 71 个独立安全漏洞；其中多项重复、3 项证据不成立，另有一批属于 HASHI 有意提供的能力。

---

## 二、默认安全模型

HASHI 的默认模型是 **受信操作员 + 受信 agent + 高风险容忍度**：

- agent 默认可以使用完整 shell、文件、浏览器和自动化能力；
- 默认不要求逐工具、逐命令或逐文件审批；
- 能力边界以操作系统账户、实例所有权和控制面入口为主，不把工具 schema 或提示词当作安全边界；
- 高风险操作依靠可追溯日志、可恢复状态、明确目标、结果验证和异常终止能力来管理；
- 面向局域网、多用户或公网部署时，在**控制面入口**增加机器身份验证；认证应由客户端自动携带，不打断 agent；
- 受限 profile 可以提供，但必须由用户主动选择，不能悄悄变成默认值。

### 修复设计硬约束

所有修复方案都应通过以下门禁：

- 不增加正常工具调用的人类审批；
- 不默认关闭 shell、浏览器 JS、文件上传、跨目录访问或长任务；
- 不使用狭窄 allowlist 代替真正的控制面身份验证；
- 不设置会误杀正常长任务的短固定超时；
- 不把“记录告警”升级成“拒绝执行”；
- 不因配置错误静默回退到一个能力更弱、行为不同的模式；应明确报错并说明配置项；
- 修复后必须验证 agent 的完整功能路径仍然可用。

## 三、修订后的优先级

### P0：立即修复，不削弱 agent 能力

|---|---|---|---|
| Workbench 控制面信任边界 | S-01、S-02、S-04、scheduler 读端点 | shell、rerun、import 本身是核心能力；问题是调用者身份不清 | 默认回环/本机；若允许非回环访问，使用实例级机器凭证或等价的透明认证。官方客户端自动携带凭证，不增加人工批准。保留任意 shell、任务导入、立即运行和输出读取能力 |

| 子进程超时后的进程树泄漏 | GD-04、scheduler finding 5 | 真实资源与恢复缺陷 | 启动独立进程组，超时/取消时先温和终止、宽限后再清理整个进程组；恢复时核验已持久化 PID/PGID。不要给所有任务增加短硬超时 |

### P1：修复语义、可靠性和显式受限模式

| 主题 | 涉及原 ID | 修订判断 | 修复建议 |
|---|---|---|---|
| `read_only` / scope 名不副实 | BB-01、BB-09、BB-13 | 默认 full-control 不变；只有用户显式选受限模式时才强制 | 将 mode/scope 检查下沉到所有执行后端，包括 `evaluate`、`session` 和 fallback。默认 profile 继续是完整能力 |
| 恢复接口与配对状态 | BB-04、BB-12、BB-14 | 属于身份恢复与数据完整性问题 | 恢复请求绑定已配对设备或本机实例凭证；提高随机强度，失败退避；重新配对采用事务更新，不静默清空有效备份。正常 agent 会话自动完成，不弹人工批准 |
| 文件读取内存与负参数 | F3、F4 | 纯 bug | 流式/分块读取；拒绝负 `offset/limit` 或定义清楚的语义；保留足够大的合法读取能力 |
| 路径解析口径不一致 | F8 | 正确性问题 | 统一相对路径基准并在返回中报告解析后的路径。不要借此把默认 `drive` 改成 workspace-only |
| `apply_patch` 阻塞事件循环 | F6、GD-03 | 两项重复，核心是调度与取消问题 | 移至异步 worker/线程；支持取消、心跳和可配置超时。默认允许长 patch，不设短固定上限 |
| 工具结果成败靠字符串判断 | GD-07 | 纯协议 bug | 使用结构化 exit status / error code，不依赖 `output.startswith("Error:")` |
| 配置值与模型回退 | RC-03、RC-04、RC-06 | 静默“安全回退”会改变功能，也不符合 HASHI 口径 | 非法 `permission_mode` 明确报错；循环数只做类型与非负校验，不设低硬上限；模型 fallback 必须可见并尊重用户 pin，允许用户配置自动 fallback |
| session 状态持久化 | RC-07 | 恢复能力缺陷 | 原子持久化 session ID 与关键续跑状态；重启后恢复，不限制 agent 能力 |

| 大目录输出 | F7 | 无界输出是资源风险，但直接截断会影响工作 | 使用分页/continuation token、流式结果或落盘引用；不得只返回“拒绝/过大”而不给继续读取的方法 |

| 主题 | 涉及原 ID | 修订判断 | 建议 |

## 四、明确不采用的“修复”

以下建议会直接伤害 HASHI 的核心能力，不应作为默认策略落地：

| 原观察 | 修订结论 | 不采用的做法 |
|---|---|---|
| F1 `access_scope="drive"` → `/` | **设计能力，不是绕过。** 应在 UI/配置中清楚标为整盘权限 | 不把现有 agent 强制迁移到 workspace-only；不默认拒绝盘外路径 |
| F2 shell/background job 不受 `access_root` 限制 | **完整 shell 的自然语义。** `access_root` 不是 OS 级隔离边界 | 不做 shell 命令 allowlist；不对命令逐次审批；不假称路径检查可以约束任意 shell |
| RC-01 Codex 关闭审批/沙箱 | **HASHI 默认执行 profile 的核心能力。** 原报告不应列为 High 漏洞 | 不移除 `--dangerously-bypass-approvals-and-sandbox`；不默认启用 Codex 沙箱；可增加醒目标识、审计字段和可选受限 profile |
| RC-08 无固定工具迭代上限 | **长任务能力。** 固定上限会制造半途退出 | 不加低硬上限；使用可配置预算、心跳、用户 stop 和异常停滞检测 |
| BB-06 无 URL host allowlist | **开放网页与本地服务访问属于浏览器 agent 能力** | 不维护默认域名白名单；远程浏览器实例依靠控制面身份和网络部署边界 |
| BB-07 任意本地文件上传 | **用户委托 agent 上传文件的必要能力** | 不默认限制为工作区文件；记录来源路径、目标站点和结果即可 |
| BB-08 已登录上下文执行 JS | **浏览器自动化核心能力** | 不禁用 `evaluate`；显式 `read_only` profile 例外 |
| BB-10 自定义 CDP URL | **多浏览器/远程浏览器配置能力** | 不限制为固定 host；验证 URL 格式并在非回环时提示部署风险即可 |
| GD-02 `telegram_send_file` 可指定路径与 `chat_id` | **跨目录发文件和选择收件人可以是明确业务功能** | 不默认绑死 `access_root` 或单一 chat；应审计调用方、目标和文件摘要，受限 profile 可另行约束 |
| GD-05 客户端选择 Telegram token | **多账号路由能力可能是有意设计** | 不直接删除参数；将其声明为显式 account/credential reference，禁止明文 token 进入日志 |
| GD-06 schema 未设 `additionalProperties:false` | schema 不是权限边界；强制拒绝未知字段会妨碍扩展与版本兼容 | 不把严格 schema 当作安全控制；可记录未知字段并通过版本化协议逐步收敛 |
| scheduler 任意 shell / import / rerun | **受信控制面的必要能力** | 不移除功能、不增加人工批准；修复入口身份和监听边界 |

## 五、纠正与删除的原结论

1. **BB-11 删除。** SSE 异常处理在循环外，取消/断连后会进入 `finally` 退订；现有证据不支持队列泄漏结论。
2. **BB-18 改写为可靠性建议。** `aiohttp.ClientSession()` 有默认超时，并非“无限期挂起”；可增加更明确的连接/空闲超时，但不得误杀长任务。
3. **RC-09 删除。** 报告所述创建任务与登记之间没有 `await`，证据不支持该并发窗口。
4. **S-03 改写。** `10.255.255.254` 位于 WSL `lo`，Windows 主机访问 `:18800` 超时，也未发现对应 `portproxy`；不能声称“已验证 LAN 可达”。当前已证实的问题是服务端绑定与只接受回环地址的客户端不一致。
5. **F1 改写。** `drive` 解析为 `/` 是有意语义，不是路径检查绕过；应作为高权限配置事实展示。
6. **重复项合并。** BB-01/08/09、BB-03/10、GD-09/10/RC-02、F6/GD-03 不能重复计算为独立漏洞。
7. **严重度统计作废。** 原汇总中的 Medium/Low 合计也有算术错误；在缺少前 17 项证据、存在重复项且产品口径改变后，不再沿用原严重度总数。

## 六、实施顺序与验收门禁

### 第一批：无功能损失的基础修复

1. 日志 `0600`、结构化脱敏、轮转与总量预算；
2. MCP/native frame 宽松可配置上限与单连接错误隔离；
3. socket 私有目录、`0600`、同 UID 校验；
4. 子进程组清理、重启恢复核验；
5. 流式文件读取、负参数校验、结构化工具状态；
6. session 原子持久化与错误隔离。

### 第二批：控制面边界

1. 单机默认统一到回环地址；
2. 非回环部署启用透明的实例级机器认证；
3. rerun/import/background shell/read API 共用同一身份中间件；
4. 保留所有原能力，官方 agent 客户端无需人工批准即可调用。

### 第三批：显式 profile 语义

1. 保持默认 profile 为 full-control / high-trust；
2. 修复主动选择的 `read_only`、scope、受限 filesystem profile；
3. 给高权限事实增加清楚的 UI/日志标识，不弹阻断确认；
4. 将严格企业策略做成 opt-in profile，而不是 HASHI 默认行为。

### 必须通过的功能回归

- agent 可无人工批准执行 shell、长测试、安装和构建；
- agent 可访问用户授权的整盘路径与盘外文件；
- agent 可执行浏览器 JS、连接配置的 CDP、上传本地文件；
- agent 可创建/导入/重跑后台任务，并读取结果；
- agent 可选择 Telegram 目标并发送任意用户授权文件；
- 长任务不会因固定短超时或低迭代上限被中止；
- 同时验证未认证的错误账户或非预期网络调用者不能直接进入控制面；
- 日志中不出现 token、cookie、Authorization、bot credential 或完整敏感 payload。

## 七、报告可信度与证据边界

- 本次复核结合了静态代码检查和有限的现场验证；原文“全部为静态分析”不准确。
- 已运行相关测试：50 passed。
- 已验证部分 scheduler/background-job 读端点在当前本机入口返回 HTTP 200。
- Windows 主机访问 Workbench 超时，不支持“当前已暴露到 LAN”的结论。
- 当前未发现 8876 浏览器网关或 9222 CDP TCP 监听；Unix 浏览器 bridge socket 存在、可连接，Chrome 扩展已连接。
- 17 条只有分类计数的旧发现，在取得 ID、代码位置、证据和审计 commit 前，不得排期或计入漏洞总数。
- 本报告记录风险与修复口径，不代表已经修改 HASHI 源码。
