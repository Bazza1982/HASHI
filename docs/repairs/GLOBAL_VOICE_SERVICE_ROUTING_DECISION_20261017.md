# Global Voice Service Routing Decision (2026-10-17)

Status: approved and implemented in HASHI3 source on
`feature-hashi-compute`. Focused source validation and direct service smoke
evidence are recorded below. Worker adoption, live frontend verification,
GitHub publication, and production promotion remain separate states.

## Ownership and boundary

- Functional owner: HERV3 voice Function.
- Catalogue owner: PAO Compute service directory plus platform voice discovery.
- Presentation owner: Frontend Connector command UI and audio delivery.
- Persistence: revisioned, private configuration for each Agent.
- Engineering layer: replaceable Function/runtime UI; Protected Core is unchanged.
- `/call`: unchanged. Call keeps its own frozen media profile and uses only the
  shared Compute catalogue contracts.

## Decision

`/voice` is an Agent voice configuration hub rather than one flat list of
voices. It separates three independent choices:

1. **Reply rules** — whether voice is off, generated by a native audio model,
   or rendered from text with TTS; whether all replies or only voice-originated
   replies speak; and whether the result is audio plus text, audio only, or text
   only.
2. **TTS services and fallbacks** — one ordered route list. Position zero is
   preferred; every later position is an explicit fallback.
3. **Semantic voice style** — an optional high-level profile. It never silently
   overwrites an exact service, engine/model, voice, speed, or performance style.

Each durable TTS route is the complete tuple of service, Compute node/offering
when applicable, engine/model, exact voice, and supported options. The UI shows
speed only for services that support it and performance style only for services
that declare it. A semantic voice profile may help choose a compatible voice,
but is never sent as a provider performance instruction. Unsupported controls
are not fabricated.

The response-format rule is Agent-wide. `text_only` prevents TTS synthesis;
`audio_only` suppresses Telegram final text when audio delivery succeeds. A
confirmed synthesis/delivery failure falls back to canonical text so the answer
is not lost. An ambiguous media receipt is never retried because that could
duplicate delivery. Text-only destinations may still receive the canonical text.

## Service catalogue and privacy

The menu is derived from qualified catalogues rather than copied model or voice
lists. Hashi Compute ordinary TTS and advanced TTS are separate services even
when they are hosted by the same node. Their advertised model, voices, speed,
style support, health, and interface remain distinct.

| Service | Privacy shown in `/voice` | Notes |
| --- | --- | --- |
| Hashi Compute TTS on configured LAN/local node | Local private (LAN/device) | Ordinary speech service; catalogue normally identifies its engine/model, such as Kokoro. |
| Hashi Compute advanced TTS on configured LAN/local node | Local private (LAN/device) | Expressive service; catalogue normally identifies its engine/model, such as MiniCPM, and declares style support. |
| Windows TTS | Local private (device) | Shows only voices actually installed on that Windows machine. |
| Device Kokoro | Local private (device) | Available only when the isolated local runtime is qualified. |
| Edge TTS | External | Speech content leaves the local-private boundary. |
| Gemini TTS via OpenRouter | External | Requires the configured credential; speech content leaves the local-private boundary. |

The configured Compute location is authoritative. An internet Compute node is
shown as external even if it offers the same model name. No local/private route
may fall through to Edge or OpenRouter unless the Agent explicitly enables
external fallback and places that service in the route chain.

Catalogue `callable` flags are descriptive compatibility metadata, not a menu
lock. Every voice supplied by the authorized Hashi Compute speech catalogue is
selectable. Preview uses the catalogue's direct, bounded sample resource; HASHI
does not regenerate a different sample and present it as the selected voice.

## Menu hierarchy

The compact first page shows the current reply mode, trigger, reply format,
ordered routes with privacy labels, external-fallback policy, and semantic
profile. Submenus then expose:

- reply mode, trigger, and output format;
- preferred voice and numbered fallbacks;
- service/provider and its availability/privacy;
- engine/model and exact voice;
- speed and performance style only when supported;
- move, replace, or remove operations for a fallback; and
- recommended private route chains.

The recommended ordinary chain is Hashi Compute TTS then Windows TTS. The
recommended expressive chain is Hashi Compute advanced TTS, ordinary Hashi
Compute TTS, then Windows TTS. Recommendations appear only when the required
catalogue services and voices are actually available.

## Persistence, migration, and failure rules

Legacy provider/voice settings are normalized in memory into one route without
writing during a read. Legacy native reply format becomes the Agent-wide reply
format. A user action performs one revision-checked write; conflict or committed
durability failure is reported and never blindly retried.

Endpoint URLs, credentials, executable paths, model caches, and privacy labels
are not copied into Agent configuration. They are resolved from their owning
catalogues at use time. Runtime-only Kokoro paths are re-derived from the current
qualified isolated runtime.

Each route has its own failure cooldown identity. Therefore a failed advanced
Hashi Compute offering may fall back to ordinary Hashi Compute on the same node.
External fallback is disabled by default and remains an explicit Agent choice.

## Validation and adoption record

Focused validation covers per-Agent isolation, legacy migration, reply rules,
ordered route editing, independent Compute offering cooldowns, privacy fencing,
direct catalogue previews, Windows/Edge/Kokoro/OpenRouter/Hashi Compute provider
boundaries, audio-only text suppression and safe text fallback, native audio
compatibility, localized menu rendering, semantic-profile/performance-style
separation, the Compute input boundary, and unchanged Call catalogue behavior.
The final focused suites completed with 400 passing and 3 skipped tests.

A direct HASHI3 smoke check discovered the same two LAN services used by the
menu and successfully produced OGG audio from each on the first attempt:
ordinary `tts` with `kokoro-82m`, and expressive `advanced-voice` with
`minicpm-o-4.5-zh-female` plus a performance instruction. This proves directory
resolution, provider execution, and audio conversion for those requests. It is
not evidence that the running Worker adopted the source or that a frontend menu
interaction completed.

This document records source behavior only until the HASHI3 Worker adopts the
generation and the named frontend completes live acceptance. It does not claim
that HASHI4, GitHub `main`, or production has received the change.
