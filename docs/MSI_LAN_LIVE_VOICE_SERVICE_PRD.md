# MSI 局域网实时语音 API 产品需求文档（PRD）

> 状态：供实现与验收使用
>
> 接口标准制定方：本项目需求方 / 调用方团队
>
> 服务实施与运维方：MSI
>
> 目标硬件：单张 NVIDIA RTX 3090
>
> 服务目标：局域网内任意获准客户端均可调用；最多 3 路实时会话；7×24 小时运行
>
> 参考实现：HASHI1 当前 Live Voice 配置与调用流程，仅用于兼容性验证

## 1. 产品定义

MSI 提供一个长期在线、面向通用客户端的局域网实时语音 API。调用方可以是任何获准接入局域网的应用或设备，包括浏览器、手机、桌面客户端、脚本以及任意 HASHI 实例。客户端无需属于某个 HASHI 实例，也无需预先登记到 HASHI。

API 不要求 API Key。服务只对配置为可信的局域网开放；通过网络边界、主机防火墙和浏览器来源检查限制访问。任何能从获准局域网访问服务的客户端，都可以按公开 API 契约创建自己的语音会话。

HASHI1 是本项目可用来验证现有调用流程的参考客户端。它帮助双方对齐实时音频、会话恢复和语音风格等语义，但不限定 API 的所有者、访问对象或未来客户端范围。

## 2. 产品目标

### 2.1 必须交付

1. **通用 API**：任何符合公开协议、能够访问获准局域网的客户端都可以使用，不依赖 HASHI 专属身份字段或 HASHI 后端。
2. **三路实时并发**：最多 3 名用户同时保持语音会话并交错说话、接收语音回复；通过 GPU 动态调度保证各会话响应，不得把整通会话串行化。
3. **动态排队**：容量已满时，新会话收到明确队列位置、等待估算和持续状态更新；取消可立即出队。
4. **低延迟 Live 体验**：双向流式音频、实时转写、语音活动检测、自然打断、静音、结束、重连和会话续接。
5. **丰富语音控制**：支持模型提供的预设性别呈现、音色、语言、语气、韵律控制，以及调用方自定义风格说明和提示词。
6. **全天运行**：开机自启、模型常驻、健康检查、自动恢复、资源监控、日志轮转和无人值守运维。
7. **单卡可行性**：以上并发和体验目标必须在单张 RTX 3090 上通过实测；若当前模型实现达不到，MSI 负责优化调度、缓存或模型服务层，并提交量化瓶颈和改进结果。

### 2.2 本期不做

- 不向公网开放，不建设公网账号、计费和 API Key 系统。
- 不要求客户端是 HASHI，也不要求客户端向 MSI 证明 HASHI 身份。
- 不规定客户端必须采用某一套 HASHI Conversation、Agent、PCM 或持久历史实现。
- 不要求逐字复制 OpenAI 的私有实现；要求提供相近的实时语音能力，并公开稳定、可供多种客户端使用的接口。

## 3. 用户与调用场景

### 3.1 目标调用方

- HASHI1、HASHI2、HASHI3、HASHI4 等 HASHI 实例。
- 手机浏览器、桌面浏览器和原生移动应用。
- Workbench 或其他本地 Web 应用。
- 通过 HTTP、WebSocket 或 WebRTC 接入的内部工具与脚本。

调用方只需理解公开 API 和服务端公布的 capabilities；MSI 不需要针对每个调用方定制端点。

### 3.2 典型体验

- 用户打开任意客户端，选择声音与表达风格，直接开始说话。
- 说话过程中模型逐步理解并流式回答；用户可以随时打断。
- 多个用户同时使用时，系统让每个会话保持有界响应。
- 资源满载时，新用户能看到排队状态，而不是遇到长时间无反馈或请求超时。
- 网络短断后，客户端可以恢复自己的会话和事件进度。

## 4. 目标架构和责任边界

```text
任意局域网客户端
（浏览器、手机、应用、脚本、HASHI 实例）
        │ HTTPS / WSS 信令；WebRTC 实时音频
        ▼
MSI Voice API Gateway
（通用会话、队列、控制、事件、健康检查）
        │ 本机私有 IPC / loopback
        ▼
常驻模型服务与音频处理器
（共享模型权重；每会话独立运行状态）
```

| 范围 | 责任方 |
|---|---|
| 对外 API 契约、字段语义、错误码和兼容版本 | 本项目需求方 / 调用方团队 |
| 模型、音频链、Gateway、GPU 调度和音色目录 | MSI |
| 每个应用自己的用户身份、产品界面和长期会话历史 | 各调用方自行管理 |
| MSI 上的临时 Live Session、媒体状态、短期恢复数据 | MSI |

MSI 管理的是通用实时语音运行会话。调用方可以携带指令和当前上下文；调用方自己的账号、权限和长期对话历史仍由该应用负责。MSI 不依赖单一调用方来解释这些数据。

## 5. 三路并发与动态排队

### 5.1 并发的验收含义

“最多 3 个同时请求”指 3 个用户可以在重叠时间内维持实时语音会话、交错说话并收到响应。三个完整电话先后串行处理不算并发通过。

- 每个会话有独立的上下文缓存、音频缓存、TTS 状态、取消标志、输出队列和临时资源。
- 模型权重默认只在显存中加载一份；不可为了并发默认启动三个完整模型副本。
- GPU 工作以有界短时间片在会话间轮转；长回复不能无限独占 GPU。
- 静音或仅监听的会话不持续占用推理计算槽。
- 一个客户端网络慢、取消或异常，不得阻塞其他客户端。

### 5.2 调度规则

调度器实现可由 MSI 选择，但效果必须满足：

1. 挂断、取消、打断、静音、心跳等控制操作优先处理。
2. 正在到达的音频和语音活动检测及时处理。
3. 已开始的语音回复获得有限连续性，避免音频断裂。
4. 新回合公平获得首包机会；排队时间越久优先级越高。
5. 采用公平轮转或等价防饥饿策略；高频客户端不能长期挤占其他用户。

### 5.3 满载行为

- 允许最多 3 个实时会话同时处于接入/推理服务状态。
- 第 4 个及之后请求进入有界队列，建议默认最多 12 个等待请求。
- 排队响应应立即返回 `queued`、位置、估算等待时间和 `request_id`；队列变动通过事件推送。
- 用户取消后立即释放队列位置。
- 队列满时返回稳定错误 `capacity_exhausted` 和建议重试时间，不得静默丢弃。
- 已建立会话的恢复、短断重连和控制操作优先于全新排队请求。

## 6. 语音、声音和提示词能力

### 6.1 实时语音能力

P0 支持：

- 实时双向音频和流式语音输出。
- VAD/断句、增量输入转写和增量输出转写。
- 用户插话后停止当前播报，并让后续回复进入新一轮。
- 静音、取消回复、结束会话和断线恢复。
- 中文、英文及 capabilities 明确列出的其他语言；不支持的语言必须明确告知客户端。

### 6.2 语音目录

`GET /v1/voices` 返回版本化 Voice Catalog。每个音色至少包含：

- 稳定 `voice_id`、显示名和版本。
- 性别呈现：`feminine`、`masculine`、`neutral` 或 `unspecified`。
- 音色说明，如明亮、低沉、柔和、清晰。
- 支持语言、表达风格和韵律控制范围。
- 是否基于参考音频、来源/许可状态及可用范围。

首期风格至少覆盖：`natural`、`warm`、`clear`、`calm`、`lively`。实际名称可扩展，但须通过稳定 ID 和 capabilities 对外公布。

### 6.3 会话自定义

- 接受调用方提供的 `instructions`、语言、风格预设和自定义风格文本。
- 自定义风格文本上限至少 1,200 字符。
- 若模型支持，可调节语速、音高、能量、表现力、情绪强度和停顿。
- 每个可选参数需公布支持范围；不支持的参数必须明确报错或返回可见降级说明，不能静默忽略。
- 创建会话后返回 `effective_voice_config`，说明最终实际生效的声音和风格。
- 风格指令只控制声音表达，不可覆盖服务安全规则或调用方自己的权限逻辑。

### 6.4 定制音色

- P0 提供管理员预先登记和版本化的参考音色。
- P1 可选支持会话级参考音频；仅在 capabilities 标明支持时开放。
- 临时参考音频仅限当前会话，结束后删除，不进入普通日志或长期训练数据。

## 7. 通用 API 契约

### 7.1 设计原则

- API 由公开、稳定的 HTTP/WebSocket/WebRTC 契约构成，不包含 HASHI 专有字段作为必填条件。
- 所有客户端使用同一套会话、音频、事件和控制语义。
- 模型通过 `/v1/models` 提供稳定服务 ID；不得要求客户端填写 MSI 本机模型文件路径。
- 请求中的 `client_label`、`metadata` 等仅作关联和诊断，不构成身份认证。
- 除本机管理端点外，任何获准局域网客户端都能调用服务 API。

### 7.2 P0 端点

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/v1/models` | 稳定模型 ID、能力和模型版本 |
| GET | `/v1/live/capabilities` | 协议、音频、并发、队列和恢复能力 |
| GET | `/v1/voices` | 音色与风格目录 |
| POST | `/v1/live/sessions` | 创建实时会话并交换 WebRTC SDP |
| GET | `/v1/live/sessions/{session_id}` | 查询本会话状态及队列信息 |
| POST | `/v1/live/sessions/{session_id}/resume` | 续接短断会话及事件游标 |
| POST | `/v1/live/sessions/{session_id}/cancel` | 取消排队或生成；可选结束会话 |
| GET / WS | `/v1/live/sessions/{session_id}/events` | 订阅实时事件或按游标续读 |
| POST | `/v1/live/sessions/{session_id}/controls` | 静音、取消回复、结束等控制 |
| GET | `/health/live` | Gateway 进程存活 |
| GET | `/health/ready` | 模型、语音链和调度器就绪 |

P1 可提供 `POST /v1/audio/speech` 和 `POST /v1/audio/transcriptions`，供不需要持续 WebRTC 会话的普通 API 客户端使用。

### 7.3 创建会话请求示例

```json
{
  "model": "msi-live-voice",
  "instructions": "以自然、清楚的方式和用户交谈。",
  "input": [],
  "voice": {
    "voice_id": "zh-warm-feminine-01",
    "language": "zh-CN",
    "style": "warm",
    "style_instructions": "语速自然，耐心但不拖沓。",
    "prosody": {"pace": 1.0, "pitch": 0.0, "energy": 0.55}
  },
  "transport": {"type": "webrtc", "sdp_offer": "..."},
  "client_request_id": "调用方生成的幂等 ID",
  "metadata": {"client_label": "mobile-app"}
}
```

创建响应至少包含 `session_id`、`sdp_answer`、`state`、`protocol_version`、`model_revision`、`voice_revision`、`effective_voice_config` 和会话限制。满载排队时还包含 `queue_position` 与 `estimated_wait_ms`。

`session_id` 必须是高熵、不可预测的会话句柄，用于隔离该会话的事件和控制；它不是全局 API Key。相同 `client_request_id` 重试必须返回同一个创建结果，避免响应丢失后重复占用 GPU。

### 7.4 实时事件

至少支持以下事件或在 capabilities 中声明的等价标准事件：

- `session.queued`、`session.queue.updated`、`session.started`、`session.closed`
- `input_audio.speech_started`、`input_audio.speech_stopped`
- `input_audio_transcription.delta`、`output_audio_transcript.delta`
- `output_audio.delta`、`response.started`、`response.done`
- `response.function_call_arguments.done`（可选工具/任务移交）
- `session.input_audio.muted`、`session.input_audio.unmuted`
- `error`

每个事件需有递增 `event_id`、`session_id`、时间戳和事件代际。客户端可从已确认的 `event_id` 继续读取；重复事件可去重。原始音频帧不写入普通事件日志。

### 7.5 控制与错误

控制至少包括 mute、unmute、response cancel、session end、heartbeat 和 context append。控制必须幂等并返回操作收据。

错误响应至少包含 `code`、`message`、`retryable`、`request_id`、适用时的 `retry_after_ms` 和不含敏感内容的 `details`。P0 错误码包括：

- `capacity_exhausted`、`queued_timeout`、`service_draining`
- `unsupported_model`、`unsupported_voice`、`unsupported_style_control`
- `context_too_large`、`invalid_audio_format`
- `session_not_found`、`session_expired`、`stale_session_generation`
- `gpu_oom_guard`、`worker_unavailable`、`internal_error`

### 7.6 能力协商

Capabilities 至少声明协议版本、模型、并发上限、队列上限、输入/输出格式、采样率、codec、上下文限制、语音目录版本，以及 VAD、barge-in、resume、event cursor、工具移交、参考音色和韵律参数支持情况。客户端不能假定服务支持未声明的功能。

## 8. 音频与连接

- 实时媒体优先使用 WebRTC/Opus；Gateway 内部标准格式建议为输入 PCM16 mono 16 kHz、输出 PCM16 mono 24 kHz，并以 capabilities 公布真实格式。
- 语音必须增量输出，客户端不应轮询 MSI 本机 WAV 文件。
- 每个会话的缓冲区有硬上限；慢客户端通过背压或丢弃过期帧处理，不能拖慢全局服务。
- 打断后停止并清除旧回复，迟到的旧音频不能覆盖新回合。
- 若浏览器/手机需要直接采集麦克风，LAN 服务必须提供 HTTPS/WSS 及设备可信任的局域网证书；纯 HTTP 页面通常无法获得浏览器麦克风权限。
- 为手机和浏览器提供稳定的局域网主机名与证书安装说明；原生客户端和脚本也可使用同一 API。

## 9. 会话、恢复和数据保留

```text
queued → connecting → active → recovering → active
                         └────→ ending → ended
任何状态 ─────────────────────→ failed / interrupted
```

- 服务维护每个活动会话的运行状态，以支持实时交互、短断恢复和事件续读。
- 默认不长期保存音频或对话内容；调用方按需发送上下文，服务不得自行把内容用于训练。
- 心跳和租约时限由 capabilities 公布；建议心跳间隔 10 秒、45 秒失联后恢复或清理。
- 单个媒体 Provider Session 可定期 rollover；建议最长 30 分钟并在到期前平滑续接，避免 Live Call 中断。
- 恢复请求带 `session_id` 和最后事件游标；恢复后旧代际迟到的音频、事件和控制必须被拒绝。
- 创建响应丢失时用相同幂等 ID 重试，不得盲目创建重复会话。
- 更新或维护时进入 `draining`，停止接收新会话，排空或迁移现有会话后再更新 Worker。

## 10. 全天运行与运维

- Windows Gateway、Supervisor 和模型 Worker 在开机后自动运行，不依赖用户登录、远程桌面或可见终端。
- Supervisor 使用单实例锁和受控退避，防止重复进程与崩溃重启循环；Gateway 故障时尽量只恢复故障组件。
- `/health/live` 表示 Gateway 仍在工作；`/health/ready` 只有在模型、音频编解码、TTS/声码器、Voice Catalog 和调度器均就绪后才返回 ready。
- 启动执行不含用户数据的短音频自检；失败时不得标记 ready。
- 监控 GPU 显存、利用率、温度、功耗、排队时长、每会话延迟、音频丢包和 Worker 重启次数。
- 资源达到 OOM 安全水位时先保护现有会话并清楚拒绝新工作，不得让 Gateway 无响应。
- 所有缓存、事件队列、映射、日志和临时文件均有容量上限及自动清理。
- 日志按时间和大小轮转；故障记录原因码、时间和恢复结果。
- 运维手册需涵盖开机检查、服务健康、升级、回滚、证书续期、显存异常和夜间故障恢复。

## 11. 无 API Key 的局域网安全

服务不要求 API Key。访问边界按以下方式实施：

- 只绑定 MSI 指定的局域网地址；不绑定公网接口，不启用 UPnP，不配置公网端口转发。
- Windows 防火墙开放给配置好的可信局域网/VLAN 或管理员指定的局域网网段，不写死为 HASHI1 单机白名单。
- 本机 Worker 仅监听 loopback 或私有 IPC，不直接暴露给局域网。
- 管理接口仅本机或单独管理网段可访问；普通语音 API 面向整个获准 LAN。
- 浏览器来源按管理员配置的 LAN Origin 检查；API 不使用 Cookie 凭证，避免跨站页面借用户凭证调用。
- WebRTC 浏览器调用使用 HTTPS/WSS 与受信任的局域网证书；TLS 用于防止局域网内窃听和伪装，不是 API Key。
- 会话 ID 高熵且不可预测；客户端只能读取或控制其持有会话句柄的会话。
- 由于不使用 API Key，任何获准 LAN 客户端都可能消耗共享 GPU 资源；服务以三路并发上限、排队、速率限制和管理端网络范围控制影响。
- 若服务未来需要跨越可信 LAN、访客 Wi-Fi 或互联网，必须重新评审网络身份认证和加密边界后再开放。

## 12. 隐私与日志

- 默认不保存原始音频，也不使用调用内容训练模型。
- 普通日志不记录完整提示词、上下文、转写正文、SDP 或参考音频。
- 可记录请求/会话 ID、状态、长度、延迟、模型与音色版本、资源水位和错误码。
- 若管理员开启诊断采样，必须可配置、限量、设置自动删除时间，并明确标注采集范围。
- 会话结束后自动清理音频缓冲、模型上下文和临时文件。

## 13. 服务目标（SLO）

在合格 LAN、正常硬件温度和通过验收的模型配置下：

| 指标 | P0 目标 |
|---|---:|
| 月度服务可用性 | ≥ 99.9%，不含公告维护 |
| 活跃实时会话 | 3 路 |
| 三路重叠说话与生成 | 必须通过，无串音、无饥饿 |
| 用户断句至首个可听回复 | P50 ≤ 800 ms；P95 ≤ 1,500 ms |

## 15. 实施阶段

### 阶段 A：通用契约与单路基线

- 冻结公开 API v1 草案、模型 ID、Voice Catalog 和 capabilities。
- MSI Gateway 提供 health、models、voices、session 创建及单路 WebRTC 语音。
- 使用通用浏览器客户端完成转写、流式回复、静音、打断和结束。
- 使用 HASHI1 作为额外兼容测试客户端。

退出条件：至少一种非 HASHI 客户端和 HASHI1 均可建立 30 分钟语音会话。

### 阶段 B：三路并发和动态排队

- 完成每会话隔离、短时间片 GPU 调度、队列更新、取消和满载响应。
- 加入背压、慢客户端和 OOM 水位保护。

退出条件：三路重叠说话和回复连续运行 8 小时，无串音、饿死、状态覆盖或 OOM。

### 阶段 C：7×24 服务化和恢复

- 部署 Windows Supervisor/Service、开机自启、健康检查、告警和维护模式。
- 完成幂等重试、事件游标、断线恢复、会话 rollover 和 Worker 崩溃恢复。
- 配置 LAN HTTPS/WSS 证书、防火墙范围和运维/回滚手册。

退出条件：故障注入通过，服务无人操作时能检测、恢复并发出准确告警。

### 阶段 D：资格验收

- 72 小时三路混合压力测试。
- 随后 7 天实际观察运行。
- HASHI1 兼容测试通过，至少一种独立通用客户端通过。

退出条件：全部 P0 验收项通过，无未解释的服务中断或会话隔离问题。

## 16. 验收场景

### 16.1 通用性

1. 不提供 API Key、不提供 HASHI 身份字段的普通 LAN 客户端可以读取 models、capabilities、voices 并建立会话。
2. 浏览器、手机或第二种独立客户端使用同一套 API 完成语音会话。
3. 任意 HASHI 实例可按公开 API 调用；新增实例无需 MSI 侧新增专属白名单逻辑或端点。

### 16.2 实时语音与风格

1. 三名用户同时连接，并使用不同语言、音色和风格。
2. 三人交错说话并同时触发回复，每个人只听见自己的会话。
3. 在回复播报期间插话，旧音频按 SLO 停止，新回合接续。
4. 更换 voice/style 后，新会话采用新设置，其他活动会话不受影响。
5. 自定义风格文本有可听差异；不支持的韵律字段会明确报告。

### 16.3 容量与公平性

1. 三路持续负载时，长回复不能使另外两路无限等待。
2. 第四个请求立即进入队列并持续收到位置变化；空位释放后自动接入。
3. 排队用户取消后立即离队；队列满时收到明确错误和重试建议。

### 16.4 恢复与长时运行

1. 创建响应丢失后用相同幂等 ID 重试，不创建重复会话。
2. 短暂断网后按事件游标恢复，无重复播报或事件错序。
3. 终止 Worker 后 Supervisor 在 60 秒内恢复，不产生重复 Gateway/Worker。
4. 触发显存保护时，现有会话继续工作，新请求明确排队或拒绝。
5. 服务进入 draining 后不接新会话，活动会话结束或平滑续接。
6. 连续 72 小时后无持续增长的显存、内存、句柄、临时文件或日志占用。

### 16.5 网络与隐私

1. 配置的可信 LAN 客户端无需 API Key 即可调用；网络范围之外的设备无法访问。
2. 公网扫描不可到达 MSI Voice API。
3. 手机浏览器在安装/信任局域网证书后可正常获得麦克风权限并建立 WebRTC。
4. 普通日志中不存在原始音频、完整提示词、转写内容或参考音频。
5. 一个会话不能读取或控制另一个会话的音频、事件、配置和临时资源。

### 16.6 HASHI1 兼容参考测试

1. HASHI1 可通过 Provider 适配器使用公开 API 完成创建、流式事件、静音、恢复和结束。
2. HASHI1 的 Phone 声音设置能映射到公开 `voice` 字段。
3. HASHI1 前端不需要 MSI 专属分支；其他客户端也不被要求模拟 HASHI 字段。
