# Lily Memory and Wiki Windows independence (2026-10-02)

Decision owner: PCM. Engineering layer: an independent Windows application and Windows Task Scheduler, outside HASHI Core, Functions, and instance configuration. The current user approved implementation of the previously saved independence plan on 2026-10-02. Lily owns operation and review.

## Decision

The authoritative consolidated memory and Wiki state now live under `%ProgramData%\LilyMemoryWiki\data`. A separately pinned Python environment, source package, local BGE-M3 model, encrypted model credential, receipts, logs, backups, and operator runbook live under the same Windows installation. The Obsidian vault remains the presentation destination; only its two generated zones can be written by the publisher.

The independent center consumes versioned batches from its own inbox. It validates registered source identities, target, schema, privacy, record count, payload SHA256, and immutable batch identity before import. Database commit precedes a per-batch ACK that binds source, target, batch ID, manifest and payload hashes, and record count. Repeated delivery is idempotent; a conflicting reused batch ID fails closed. Source pending is untouched. An optional local exporter and a read-only compatibility bridge for the old remote landing directory are producers, not center dependencies. A source outage is recorded as delayed input; it does not block processing of already delivered data.

The compatibility bridge reuses the importer's ACK validator before treating an old-location batch as already delivered. It checks the success format and status, source, destination, batch identity, both hashes, record count, and accepted/duplicate totals. An inconsistent ACK fails closed and leaves the source batch in place.

Local dense embedding uses the standalone BGE-M3 snapshot. The pooled output was compared with eight pre-migration vectors (cosine 0.9737–0.9824); the raw CLS output was incompatible. Wiki classification and discovery use an explicitly configured direct model endpoint and a machine-scope Windows DPAPI protected key with restricted file ACL, never a HASHI Agent runtime or repository secret lookup. The Wiki completion gate reads the independent import/embed receipt and database counts. Publishing retains staging, page backups, history/latest manifests, evidence and privacy checks, and generated-zone enforcement.

## Adoption and evidence

The two SQLite databases were copied by SQLite backup into the independent installation, with matching source and target counts, schema, and Wiki watermarks. The old databases and migration snapshots are retained. Eight focused standalone tests cover immutable ACK/idempotence, fail-closed invalid input, inconsistent legacy ACK rejection, post-commit ACK recovery, missing model credentials, publisher path confinement, missing exporter batch detection, and consistent daily backup/retention. Two isolated shadow Wiki publications succeeded; the second also ran with the optional HASHI source path deliberately unavailable while center import, embed, and Wiki continued.

At production cutover, the three former Lily HASHI Scheduler writers (`lily-remote-memory-import-prewiki`, `lily-memory-consolidation`, `lily-wiki-daily-update`) were disabled and verified to have no pending recovery. The independent center accepted three batches, added 40 records, recognized 26,530 duplicates, issued three byte-bound ACKs, and embedded all 40 new records. The first independent Wiki publication returned exit code 0, created one page, updated 13, retained staging/backups/history/latest manifests, reported zero validation failures, and touched no path outside generated zones. The seven new tests passed. A real Task Scheduler launch of the independent diagnostic task returned exit code 0 and completed a direct model preflight. A separate read-only task also fired automatically on its timed trigger with exit code 0. Six daily Windows tasks were enabled for a 00:15 SQLite state backup, the source adapter, legacy ingress adapter, ingest, embed, and Wiki phases. Catch-up runs wait for same-day upstream receipts so a late Windows login cannot silently run the phases out of order.

On 2026-10-02, a further local rehearsal left the remote sender and its delivery address unchanged. One synthetic batch in the isolated shadow old-location directory was validated and copied to the standalone shadow inbox. Import accepted one record and issued an ACK matching source, destination, batch ID, both SHA256 values, and record count; repeated bridge runs did not redeliver it, and the old source batch remained. Embedding completed the one pending record. Shadow Wiki finished with exit code 0, updated one generated page, matched its latest/history manifests, and reported zero publication gate failures or generated-zone violations. A focused test first reproduced the bridge's acceptance of an inconsistent ACK, then passed after the shared ACK validator was used; all eight standalone tests passed. The temporary shadow source configuration was restored after rehearsal.

The Windows Task Scheduler was then used to launch the four production phases in order under their configured task identity. The compatibility bridge found two previously handled old-location batches; ingest reported zero new batches, embed reported zero pending records, and Wiki completed with exit code 0. Production Wiki created two generated pages and updated one from existing discovery backlog. Its report and latest/history manifests matched, all validation gates were zero, and no path outside generated zones was written. All six enabled Windows tasks now have successful last-run results. The first regular overnight Windows trigger has not yet occurred; its outcome must still be checked from task history and per-phase receipts. These are operational observations, not source or artifact claims.

## Boundaries and follow-up

Core files and running HASHI Workers were not changed or restarted. The old source export and legacy incoming directory remain compatibility inputs, so remote senders need a separate delivery change before those adapters can be retired. Import ACK files are local center receipts; they do not prove HChat delivery or source-side cleanup. The six tasks use the same user's limited S4U token, so they can run after logout. A scheduled S4U diagnostic decrypted the independent DPAPI credential and reached the direct model endpoint; a scheduled S4U backup wrote a verified SQLite snapshot. The first complete overnight cycle remains unobserved. Operators should use the installation's `docs\OPERATIONS.md` and receipt files; do not re-enable the old Scheduler writers while Windows tasks are active.
